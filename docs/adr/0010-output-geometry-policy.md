# Output geometry policy — world-cubic chunks and an anisotropy-aware pyramid

**Status:** Accepted (2026-08-24); amended by [Follow-up (issue #85)](#follow-up-issue-85), which refines the isotropy yardstick, the axis floor and the depth stop where implementation found the rule below underdetermined, by [Follow-up (issue #86)](#follow-up-issue-86), which settles what the coarse-level stopping rule is applied to and what depth records when no level reaches the bounds, by [Follow-up (issue #87)](#follow-up-issue-87), which records what making `downsample_method` load-bearing touched, by [Follow-up (issue #88)](#follow-up-issue-88), which verifies the "applies uniformly" claim against all three write paths and records what 2D output actually costs, by [Follow-up (issues #111, #114)](#follow-up-issues-111-114), which changes how the policy is executed — one written level feeding the next — without changing the policy, by [Follow-up (issue #113)](#follow-up-issue-113), which measures what the chunk target costs a consumer, confirms the 512 KiB default against a whole-slide scene, and records why the sharding rejection's reasoning is unchanged while its price is now known to be much higher, by [Follow-up (issue #117)](#follow-up-issue-117), which **reverses that rejection** and ships sharding as opt-in `Geometry` fields (`shard_target_bytes`, `shard_shape`) defaulting to off, by [Follow-up (issue #112)](#follow-up-issue-112), which extends the policy back over the reader's blocking so source tiles nest in the planned write grid instead of being split into it, by [Follow-up (issue #124)](#follow-up-issue-124), which replaces the sharding arithmetic with a measured full-scale run and corrects this ADR's prediction that a sharded store would be larger, and by [Follow-up (issue #126)](#follow-up-issue-126), which measures the same store written both ways at one chunk shape and establishes that sharding cannot change compression at all, its whole cost being the shard index.

Zarrmony plans an output store's [geometry](../../CONTEXT.md) itself instead of delegating chunk shape to `bioio-ome-zarr`'s memory-target heuristic. Chunks are the largest power-of-two shape whose raw size fits a **512 KiB** target and which is closest to cubic **in micrometres**, computed per level from that level's physical voxel spacing. The pyramid halves every spatial axis whose spacing is within `isotropy_tolerance` (default `1.5`) of the finest axis, so levels move toward isotropy and the scarce axis is spent last. Pyramid depth is the **greater** of the existing `pyramid_min_size=256` Y/X rule and the depth at which a level becomes a coarse level — `Z·Y·X·itemsize ≤ 64 MiB` and `max(Y, X) ≤ 2048` — with an axis floor of 32 voxels and no halving of an axis already below it. Mean-pool remains the downsampler; `downsample_method` exposes `"max"` for sparse-label acquisitions. The policy applies uniformly to per-scene, bf2raw and plate output, and is carried by a single frozen `Geometry` object rather than by loose keyword arguments; `chunk_shape` and `pyramid_min_size` survive on `convert()` as retained sugar that folds into it. Sharding is deliberately not implemented. This ADR is decisions-only; implementation is unsliced.

The three bounds borrowed here — 64 MiB per (t,c), 2048 long axis, 32-voxel floor — are Lucida's `SourceCoarseConfig` defaults, adopted knowingly (see Consequences) and exposed as `Geometry` fields so a store can be planned for a different consumer.

## Why these numbers

Every constant traces to a measurement rather than to taste. The reference dataset is a SmartSPIM whole-brain acquisition, `(1, 3, 3627, 8835, 7452)` uint16 at Z 2.0 / Y 1.8 / X 1.8 µm — 1.30 TiB raw, ~283 GB converted.

- **512 KiB raw chunk target.** Two measured constraints meet there. Lucida's transport study (`docs/research/source-read-concurrency.md`) puts interactive source reads at **p50 325 KiB** with a flat **~110 ms TTFB** per object, and flags ~5 MB objects as bandwidth-bound rather than round-trip-bound; sampling the converted store's own level-0 chunks gives blosc-zstd ratios of **2.3–4.2× on tissue**, so 512 KiB raw lands at ~150–220 KiB compressed, near that band. On the other side, `MAIN_VIEW_UPLOAD_BUDGET_BYTES` is 8 MB of _decoded_ bytes per frame, so 512 KiB decoded admits 16 chunks per frame.
- **What the old default did.** With `chunk_shape=None`, `multiscale_chunk_size_from_memory_target` fills the rightmost axis first under a 16 MiB budget, producing `[1,1,1,1125,7452]` at level 0 — a full-width, single-Z-plane slab of 15.99 MiB. One chunk exceeds a whole frame's upload budget (0.48 chunks/frame), and because the chunk spans the entire X extent, frustum culling has exactly one column to choose from and can never trim it.
- **The size of the defect.** Fetching a 512³-voxel region at the centre of the volume costs 1,024 chunks and 17.2 GB to deliver 268 MB of wanted voxels — **1.6 % efficiency**. At 64³ it costs 512–729 chunks and 268–382 MB, ~70–100 %.
- **The clearest statement of it.** Lucida's admission window is `max(64, 4 × concurrency) = 64` requests, drained centre-out. Under the old geometry those 64 requests buy 64 whole-brain Z planes — 128 µm of Z across the full 15.9 × 13.4 mm, almost all off-screen. At 64³ the same 64 requests buy a 256³ cube: **461 × 461 × 512 µm centred on the camera**.

## Considered Options

- **Keep delegating chunk shape to `bioio-ome-zarr`'s memory-target heuristic.** Rejected. The heuristic is not wrong so much as dimensionally blind: it grows the rightmost axis first under a byte budget, which is the right answer for a 2D plane and the wrong answer for anything with a Z extent. On a wide volume it always converges on full-width single-plane slabs, and the failure is silent — the store validates, opens in napari, and only misbehaves under a 3D camera. Nothing about the heuristic can be tuned to avoid this from the caller's side; the only lever is `chunk_shape`, which forces the caller to compute per-level shapes by hand. Owning the planner is the smaller maintenance burden.
- **Fixed voxel-cubic chunks (`64³` everywhere), clamped to the level shape.** Rejected, though it captures most of the win — against 1.6 % efficiency it is a 40–60× improvement, and on near-isotropic data it is exactly what the chosen rule returns. It fails on anisotropic acquisitions: a 10:1 confocal stack (Z 5 µm, XY 0.5 µm) gets a chunk spanning 320 × 32 × 32 µm, so culling granularity is ten times coarser in Z than laterally and asking for one 5 µm plane drags in 320 µm of stack. That is the same defect this ADR exists to remove, one order of magnitude down. Choosing it would also be internally inconsistent: the pyramid rule below treats µm/voxel as the thing that decides which axis is scarce, and there is no principled reason for fetch granularity to ignore the same fact. The world-cubic rule degenerates to `64³` whenever the data is near-isotropic, so nothing is lost on the common case.
- **Halve Z, Y and X uniformly at every level (`SPATIAL_DIMS = {"Z", "Y", "X"}`).** Rejected. It is a one-line change and it is identical to the chosen rule on the reference dataset, which makes it tempting. But it preserves anisotropy as an invariant ratio: a 10:1 stack is still 10:1 at every level, so its coarse level is a stack of slabs rather than an overview volume — again the reported symptom, relocated to the coarse tier. Worse, it halves the scarce axis at the same rate as the abundant one. In light-sheet and confocal, XY is oversampled and Z is undersampled; uniform halving destroys the information there is least of, fastest. Anisotropy-aware downsampling is the established convention for such stacks (Neuroglancer precomputed, BigDataViewer/N5 per-level factors), not a local invention. Its cost is real but bounded: on strongly anisotropic data the pyramid needs one or two extra levels, taking overhead from ~1.14× to ~1.33× of level 0, and on near-isotropic data it costs nothing.
- **Lower `pyramid_min_size` (256 → 64) rather than adding an overview-target stopping rule.** Rejected. It is one constant and it would produce a small enough level on the reference dataset — but only by accident, and it overshoots to a 1.8 MiB level where a 13.8 MiB one was needed. The deeper problem is that a Y/X voxel-count floor has no relationship to the property being sought. "Does a level exist that a viewer can hold whole?" is a question about decoded bytes and lateral extent, and any proxy for it will be right on the shapes it was tuned against and wrong elsewhere. Tying depth to the actual bound also makes the guarantee checkable at conversion time instead of discoverable in a viewport.
- **Apply `min_size` to `min(Z, Y, X)` once Z becomes a downsampled axis.** Rejected — it is the obvious generalisation and it is a regression. A 3-plane × 2048² stack has `min = 3`, below any sensible floor, so the pyramid would collapse to a single level. Such data is safe today only because Z is excluded from `SPATIAL_DIMS`. Hence the axis floor is per-axis and an axis already below it simply never halves, and hence depth is a `max()` of two rules rather than a replacement of one by the other — which also makes the change monotone: no existing conversion loses a level.
- **Max-pool the whole pyramid.** Rejected. It is what Lucida's server-side generated coarse tier already does (`DOWNSAMPLE_ALGORITHM_VERSION = "max-pool-v1"`), so adopting it would preserve the appearance users see today, and for sparse labels the difference is stark: a 15 µm soma occupies 1.6 % of one level-5 voxel, so mean-pooling renders it at 114 against a background of 100 while max-pooling renders it at 1000 against ~141. But max-pool biases every level above 0 high and makes the pyramid useless for measurement, and at high factors it lifts background toward the noise maximum — the max of 32,768 draws sits roughly 4σ out. Mean-pool is also what the OME-Zarr ecosystem assumes. The knob covers the sparse case without making it everyone's default.
- **Mean-pool the detail levels and max-pool only the coarse level.** Rejected as a default, and it is the strongest rejected option: it maps exactly onto Lucida's own two-tier model, where detail levels are for inspection and the coarse level is for navigation. But it makes the pyramid internally inconsistent, and a viewer with no coarse/detail concept — napari, vizarr — shows a visible brightness discontinuity at the moment it crosses into the last level. Shipping a default whose artefact appears only in third-party viewers is the wrong trade; a user who wants this can convert with `downsample_method="max"` throughout.
- **Gate the new policy on `Z > 1`, exempting 2D and plate output.** Rejected. It is the zero-regression choice for the HCS path and would have been defensible, but it leaves a real defect in place: a 2160² Phenix field currently gets a single `(1,1,1,2160,2160)` chunk of 8.9 MiB, which also exceeds a frame's upload budget. The objection to applying the policy — that splitting a 1080² field into nine chunks adds eight round trips — does not survive the concurrency measurement: at concurrency 16 those nine issue in parallel for one TTFB, they sit closer to the 325 KiB interactive profile than one 900 KiB object does, padded edge chunks compress to nearly nothing, and the field fills progressively rather than all-at-once. A dimensionality-dependent special case in the one place a single rule is most valuable is not worth buying a problem the measurements say does not exist.
- **Add five keyword arguments in the existing style rather than a policy object.** Rejected. Each geometry parameter currently touches ~14 sites — `convert()`'s signature, the audit dict, three dispatch calls, four internal writer helpers with eight pass-throughs, plus `cli.py`, `scene.py` and `plate.py`. Five new parameters is ~70 mechanical edits and a sixteen-parameter public signature, and the next geometry knob costs the same again. The policy object makes future additions one field. `chunk_shape` and `pyramid_min_size` are retained rather than removed, so no caller breaks.
- **Expose no new knobs; hardcode the constants.** Rejected. It conflicts with the smart-default-plus-override principle already applied across the codebase, and it would bake two numbers borrowed from another repository's configuration into zarrmony with no way to unborrow them — the one case where a knob is not optional.
- **Choose an independent overview target (e.g. 32 MiB) instead of adopting Lucida's 64 MiB.** Rejected. Margin sounds prudent but buys nothing: the bound is a `>` comparison, so a level at exactly 64 MiB passes, and on the reference dataset both targets select the same level. Deliberately diverging would risk planning a store that satisfies a self-imposed number while missing the real one. The coupling is instead made explicit and configurable.
- **Ship `shard_shape` as an opt-in `Geometry` field, defaulting to `None`.** Rejected here — **reversed by [Follow-up (issue #117)](#follow-up-issue-117)**, which ships it; the original reasoning is left standing below because what changed is one premise in it, not the analysis. This was the closest call in the ADR. The object count is the one number this policy makes materially worse — 87k to ~3.2 M for the reference store — and sharding answers it directly: a 256³ shard holds 64 chunks of 64³ and would bring that store to ~47k objects, a 68× reduction, with chunks still individually range-readable. The write side already exists upstream (`OMEZarrWriter` normalises shards per level and validates that each shard dimension divides its chunk dimension). It is rejected because `lucida-store`'s `parse_codec_chain` accepts only `[bytes]` or `[bytes, compressor]` and rejects any chain whose first codec is not `bytes` — which is precisely what a `sharding_indexed` array presents. An opt-in flag would therefore ship a trap: enabling it produces a store that fails to open with `first storage codec must be 'bytes', got 'sharding_indexed'`, an error that reads as corruption rather than as an unsupported feature. A flag shipped is a flag supported, tested and documented, and there is no consumer for it today. Revisit when Lucida gains `sharding_indexed` read support; the decision is then one field plus a default flip.
- **Build an OME-Zarr → OME-Zarr `zarrmony rechunk` command as part of this work.** Deferred to a separate issue. The migration is unusually cheap and provably lossless for stores written under the old default — because today's chunks are full-width single-plane slabs, rebuilding 64³ chunks means reading Z in bands of 64 where every input chunk is consumed exactly once, a sequential streaming pass at ~8.4 GB per channel-band, and the new pyramid mean-pools the same untouched level 0 so it yields the values a re-conversion would. That makes the tool worth building, but it is a distinct feature with its own surface — metadata-copy fidelity, `--force` semantics, resumability across a multi-hour job over millions of objects — and bundling it would delay the geometry change. The reference dataset is re-converted from source instead.

## Consequences

- **Level-0 chunks on the reference dataset go from `[1,1,1,1125,7452]` (15.99 MiB) to `[1,1,64,64,64]` (512 KiB).** Frustum culling gains real freedom on every axis; the per-frame upload budget admits 16 chunks where it previously admitted less than one.
- **The pyramid gains a level and shrinks.** Levels become `(3627,8835,7452) → (1813,4417,3726) → (906,2208,1863) → (453,1104,931) → (226,552,465) → (113,276,232)`. Because Z now halves too, each level is ⅛ of the previous rather than ¼, so levels 1–5 add ~14 % over level 0 where levels 1–4 previously added ~33 %. Smaller chunks compress somewhat worse than full-width slabs, so expect a wash to modestly smaller overall rather than a guaranteed saving.
- **Level 5 is a coarse level, and that switches off a server-side code path.** At 113 × 276 × 232 it is 13.8 MiB per (t,c) with a 276 long axis and 40 chunks, satisfying every `SourceCoarseConfig` bound; `select_source_coarse_level` returns it, `coarse_level_index` is populated, and `plan_generated_coarse_for_image` early-returns `None`, so Lucida stops generating its own max-pooled coarse tier at concurrency 1 over 1.3 TiB of source. Its appearance changes accordingly: the coarse tier becomes mean-pooled, which is dimmer for sparse structures.
- **Object count rises ~37×** on the reference dataset (87,048 → ~3.2 M; 2.78 M at level 0). Plate output rises ~4–5× — a 384-well plate at 4 fields × 3 channels goes from roughly 23k to roughly 106k objects. Irrelevant on local disk; on object storage this is listing and per-object metadata cost, and it is the pressure that will eventually reopen the sharding decision.
- **`NGFF` scale metadata needs no separate handling.** `OMEZarrWriter` derives `dataset_scales` as each level's shape divided by level 0's, per axis, so per-axis-varying downsample factors flow into `coordinateTransformations` automatically.
- **`build_pyramid` becomes shape-driven.** Deriving coarsen factors from consecutive entries of `level_shapes` rather than hardcoding `{i: 2}` makes uniform and per-axis-varying downsampling one code path.
- **Existing stores are unaffected and are not migrated.** New conversions get the new geometry; the reference dataset is re-converted from source. A `zarrmony rechunk` command is a follow-up issue.
- **The audit block records resolved geometry, not inputs.** Per-level shapes, per-level chunk shapes, the coarse level index and the downsample method replace the current `chunk_shape: None` / `pyramid_min_size: 256` pair, which was accurate and uninformative — the defect this ADR fixes was found by inspecting a viewport, not the store's own metadata.
- **A sharded store cannot be read by Lucida.** Recorded here so the constraint is not rediscovered: it is a codec-chain limitation in `lucida-store`, not a zarrmony limitation, and `bioio-ome-zarr` supports the write side today.
- **SemVer.** A minor bump. On-disk geometry changes for every new conversion, including plate output, but no API breaks — `chunk_shape` and `pyramid_min_size` keep working. The CHANGELOG should carry a migration note for users comparing new stores against old ones, and should name the object-count increase explicitly for anyone hosting on object storage.

## Follow-up (issue #85)

Implementing the pyramid rule surfaced three shapes the decision above does not settle. All three refine "halve every spatial axis whose spacing is within `isotropy_tolerance` of the finest axis, subject to an axis floor of 32 voxels"; none of them changes the reference dataset's levels, and each exists to keep the rule from misfiring on a shape the summary paragraph did not have in view. They are recorded here rather than edited into that paragraph so the decision as accepted stays legible next to what implementing it cost.

- **The isotropy yardstick is the finest _still-halvable_ axis, not the finest axis outright.** An axis pinned at its floor holds its level-0 spacing forever while every other axis doubles theirs each level, so leaving it in the comparison set lets an axis that can no longer be spent go on deciding what the others may spend. Take a `(1, 1, 1, 256, 256)` field at Z 1.0 / YX 0.5 µm: Z is frozen at one plane, and by level 2 the laterals have reached 2.0 µm — a ratio of 2.0 against the frozen Z, outside the 1.5 tolerance — so `(32, 32)` is never written. That is every 2D acquisition losing the tail of its pyramid, which is the one shape this ADR's monotonicity promise most needs to protect. Restricting the yardstick to axes the floor still permits to halve is the fix; it is a no-op wherever nothing is frozen, which includes the reference dataset. Found by an existing test failing, not by inspection — the interaction is invisible in the rule as stated because "the finest axis" reads as a property of the data rather than of the level.
- **Depth also stops once Y and X are both at their floor.** The rule as accepted halves any eligible axis and stops on the Y/X `pyramid_min_size` test, which asks whether the laterals got _smaller_ — it cannot fire when they are not moving at all. A 512-plane column over a 128² field at 0.5 µm isotropic therefore reaches `(128, 32, 32)`, freezes both laterals, and then keeps halving Z alone: four more levels that are new resolutions in name only, each one _increasing_ anisotropy, which is backwards for a rule whose whole purpose is to reduce it. So the pyramid also stops when neither lateral can ever halve again. The phrasing matters — it asks what Y and X can _ever_ do, not what they did this level — because a stack with oversampled Z legitimately spends Z alone for a level or two while the laterals wait for its spacing to catch up: `(256, 1024, 1024)` at Z 0.2 / YX 1.0 µm shrinks Z alone twice, and only then do all three axes halve together. This is a ceiling on depth, so it composes with rather than replaces the `max()` of the two depth rules. At the default `pyramid_min_size=256` it is unreachable (256 > 32, so the depth rule always bites first); it becomes load-bearing when a caller lowers the depth floor toward the axis floor, and again when the coarse-level stopping rule starts extending depth past the Y/X rule.
- **On Y and X the axis floor is capped by `pyramid_min_size`.** The two floors overlap on the lateral axes, and under any default policy the depth rule stops the pyramid long before Y or X could reach 32. The cap therefore only bites when a caller has deliberately asked for a floor _below_ 32 — and a caller passing `pyramid_min_size=8` is entitled to the levels they asked for rather than to a borrowed 32-voxel default silently overriding them. Reading the axis floor as an absolute would have cost levels on existing conversions, which is exactly the monotonicity the "Apply `min_size` to `min(Z, Y, X)`" rejection above commits to. Z keeps the uncapped 32, since nothing else bounds it.

Two things this slice did **not** change, both deliberate: pyramid depth was still the `pyramid_min_size` Y/X rule alone — the coarse-level stopping rule, and with it `coarse_max_bytes` and `coarse_max_long_axis`, was left to the next slice (#86, below) with those `Geometry` fields inert — and `downsample_method` is still unread, so mean-pool is the only downsampler in the code.

## Follow-up (issue #86)

Implementing the coarse-level stopping rule — depth as the `max()` of the `pyramid_min_size` Y/X rule and the depth at which a level satisfies `Z·Y·X·itemsize ≤ 64 MiB` per (t,c) and `max(Y, X) ≤ 2048` — settled three things the decision above leaves open. The reference dataset behaves exactly as Consequences predicts: level 5 at `(113, 276, 232)`, 13.8 MiB per (t,c), long axis 276, bought by the second rule where the first stops at level 4's 110 MiB.

- **Depth now depends on the dtype, so `compute_level_shapes` takes one.** "Can a viewer hold this level whole?" is a question about decoded bytes, and the same shape in uint8 reaches the bound a level earlier than in uint16 — on the reference volume, `(226, 552, 465)` is already coarse at 55 MiB in uint8 and still 110 MiB in uint16. A default was considered and rejected: a signature that guesses uint16 is silently wrong for the two dtypes that most change the answer, and an optional "skip the byte bound if unknown" argument turns a missing dtype into a quietly shallower pyramid. `dtype` is therefore required and positional, matching `plan_chunk_shape`, and lands before any release of the geometry series.
- **The rule tests the deepest level built so far, not every level.** Coarseness is monotone down the pyramid — each level is no larger than its parent on every axis, so once a level is inside both bounds every deeper one is too. The loop therefore asks the question once per level of the level it just kept, and `coarse_level_index` reports the _shallowest_ qualifying level, which is the most detailed one a viewer can hold whole and hence the one it wants for spatial context.
- **A pyramid with no coarse level records `null` rather than failing.** Rule 2 extends depth but does not override the two ceilings from #85: depth still ends once Y and X are both floor-frozen, and once no spatial axis is eligible at all. A volume that bottoms out there while still too large simply has no coarse level — `CONTEXT.md` already allows for this — and forcing one would mean grinding an axis below the floor the "`min_size` on `min(Z, Y, X)`" rejection above exists to protect. The audit records the fact either way, which is the point of the whole rule: `coarse_level_index` (audit schema 11, additive, per scene and per plate field) makes "does this store have a level a viewer can hold whole?" answerable from the store's own metadata.

## Follow-up (issue #87)

Reading `downsample_method` — mean or max, chosen once and applied to every level — needed no new decision: the knob, its default and the two rejected alternatives (max everywhere, mean-detail/max-coarse) are settled above. Three things it touched are worth recording.

- **No audit schema bump.** `config.geometry` has carried `downsample_method` since #83, when the field was plumbed and audited but inert. The field going load-bearing therefore changes no record shape, and a consumer already pinned to schema 11 can tell the two pyramids apart today. This is the payoff for auditing the whole resolved policy rather than only the fields that were doing something at the time: the one release where the same source could start producing two different stores is the release where the audit needed no change at all.
- **Iterative pooling stays exact under `"max"`, which is why one code path serves both kernels.** The pyramid is built level-from-level, not each level from level 0. That is exact for max — the max of maxes is the max — and exact for mean whenever the pooling windows are equal-sized, which the shape rule guarantees apart from the trailing row a `trim_excess` drops on an odd extent. So the kernel is a lookup above the loop rather than a branch inside it, and "applied uniformly" is structural rather than something the tests have to keep watch over.
- **Data-driven contrast (#53) moves with the kernel, and should.** `window.start` / `window.end` are the min and 99.9th percentile of the _coarsest pyramid level_, computed in the same dask graph so the raw data is read once (amended by the #111/#114 follow-up below: the level is now read back off the store instead, which the rest of this bullet is unaffected by). Under `"max"` that level is max-pooled, so both bounds open higher than the same conversion's would under mean. That is the right window for the pyramid actually written — a viewer auto-contrasting a max-pooled store against mean-pooled statistics would clip — and the audit records the method next to the resolved bounds, so a store's contrast is explicable from its own metadata. Worth naming because the interaction is invisible from either feature alone: #53 predates the knob, and the ADR's rejected-options analysis is about pixels, not display metadata.

## Follow-up (issue #88)

The last slice of the series checks the summary paragraph's smallest clause — "the policy applies uniformly to per-scene, bf2raw and plate output" — against what the code does, on the shape the rejected `Z > 1` gate was written about. It found nothing to fix, which is the finding, and locks it in `tests/test_geometry_parity.py` so a later change has to break it deliberately.

- **There was never a gate to remove, and that is a property of how the rule is written.** The rejection above reads as if exempting 2D were a live branch someone had to go back and delete. It was not: every rule in this ADR is expressed over _the axes that are present_, so `SPATIAL_AXES` membership and the per-axis floor do all the dimensionality work between them. A singleton Z contributes exactly one candidate length to the chunk search and a constant micrometre extent to the cubeness score, so it can move neither the winning chunk nor the depth rule; `(1,1,1,2160,2160)` in TCZYX and `(1,1,2160,2160)` in TCYX plan the same laterals. The 2D behaviour therefore changed the moment the planner landed in #84, not here. Recorded because "we decided not to special-case it" and "the shape of the rule makes the special case unexpressible" are different guarantees, and only the second one survives a refactor.
- **Parity is a property of `write_scene`, not of three parallel implementations.** All three layouts call it with the same frozen `Geometry` and it does the planning; bf2raw and plate differ only in where the store lands and what metadata wraps it. So the parity assertion that matters is that `level_shapes`, `chunk_shapes` and `coarse_level_index` are byte-identical across the three for one FOV, and that each matches the arrays actually on disk — a plan recorded in the audit that the writer then overrode would satisfy a weaker check. Both hold, per-FOV and across the FOVs of a multi-well plate.
- **On a single plane the lateral bound decides coarseness, never the byte bound.** A 2160² uint16 field is 8.9 MiB per (t, c) — an eighth of `coarse_max_bytes` — so level 0 already clears the byte bound and fails only `max(Y, X) ≤ 2048`; `coarse_level_index` is 1, the 1080² level. The consequence for anyone planning a plate store for a different consumer is that `coarse_max_long_axis` is the field to tune and `coarse_max_bytes` is inert, which inverts the volumetric case the two bounds were adopted for. Depth itself is unaffected: the Y/X `pyramid_min_size` rule reaches 270² here, four levels deep, well past what either coarse bound asks for.
- **What 2D costs, in objects, and how the plate estimate above should be read.** A 2160² uint16 field goes from 4 chunk objects — one whole plane per level, since 8.9 MiB fit the old 16 MiB budget outright — to 39: 25 at level 0, then 9, 4 and 1. That is ~10×, not the 4–5× Consequences names for plate output; the two are consistent because the multiplier is a function of field size and the plate figure corresponds to a 1080²-class field, which goes from 3 objects to 14 (~4.7×). A 2160² field is the worse end of the range, and the range is what a plate owner should plan against. Nothing else in the policy trades against object count — sharding, the mechanism that would actually answer it, is rejected above for want of reader support — so the only lever is `--chunk-target-bytes`, raised when a store is destined for object storage and its consumer is not latency-bound.

## Follow-up (issues #111, #114)

Nothing in the policy changed; how it is executed did. Building every level as one lazy graph and handing the lot to a single `da.compute` is fine at the scale the series was designed against and does not survive a whole-slide input — the coarsest level's graph reaches back through every intermediate level to the reader, and dask spends hours constructing it before writing a byte. `write_pyramid` now writes one level at a time, each pooled from the level just written and re-opened off the store.

- **The exactness argument in #87 above is what makes this legal, and it was already written down.** "Iterative pooling stays exact under `"max"`" is a claim about the kernel, not about the graph: a level pooled from disk and a level pooled inside its parent's graph are the same pixels, because both kernels are exact over a block of any shape. The single-graph build was therefore never load-bearing for correctness, only for how the work was scheduled — which is why this is a follow-up and not a new decision.
- **The contrast bullet's justification inverted.** Fusing the min/percentile into the pyramid's compute was argued as "the raw data is read once". Measured on the reference whole-slide input, the fusion was the difference between writing and not writing: a controlled A/B differing only in `contrast_percentile` wrote nothing in 610 s with contrast on while reading 200–370 MB/min. Contrast now runs after the pyramid is on disk, against the written coarsest level — which `coarse_max_bytes` already caps at 64 MiB, so the bound the policy sets for a viewer turns out to bound this pass too. Same values, same interaction with `downsample_method`, no effect on the write.
- **Read amplification is now bounded by the pyramid, not by the pyramid's depth.** Before: 25.7 GB read per 3.3 GB written, 4.2×, because every level re-derived its pixels from the base. After: level 0 reads the source once, and each level above reads back roughly a quarter of what the level below wrote — the pyramid's own bytes, about a third of level 0, and off the destination store rather than off the reader.

## Follow-up (issue #113)

A whole-slide scene — level 0 `[1, 4, 1, 140757, 171855]` uint16, 24.2 Gpx × 4 channels — is the first input to make the 512 KiB target look wrong. It projects to ~493,000 objects, and a conversion at that target ran at ~38 chunks/min: roughly nine days for one scene. A re-run at an 8 MiB target finished in 3 h 02 m at 31,156 objects, opened in napari, and resolved every level. On that evidence the issue proposed raising the default, or scaling it with image size.

**The default does not change.** The 8 MiB store is worse in the consumer that matters, for a reason no measurement in this ADR had looked for, and the arithmetic is exact rather than indicative.

- **The chunk target sets how many chunks a viewer can hold resident, and the fall-off is abrupt.** Lucida's 2D slice path sizes its atlas in `computeAtlasGeometry` (`lucida-web/src/renderer/atlasSizing.ts`), whose slot dimensions _are_ the array's chunk shape: `maxSlots = floor(budget / chunk_bytes)`, then `slotsPerAxis = floor(sqrt(maxSlots))`, then `totalSlots = slotsPerAxis²`. Against `SLICE_ATLAS_BUDGET = 64 MB`, a 2048² uint16 chunk gives `maxSlots = 8`, `floor(sqrt(8)) = 2`, **4 resident chunks**; a 512² chunk gives `maxSlots = 128`, `floor(sqrt(128)) = 11`, **121**. The square-slot-grid floor is what makes this a cliff rather than a slope — it discards half the budget at 8 MiB and 5 % at 512 KiB. Observed directly: the 8 MiB store renders four sharp chunks in a viewport and low-resolution context everywhere else. Resident _area_ is only ~1.9× better at 512 KiB, since the budget is in bytes; what improves 16× is the granularity with which that area can be placed against the camera, and the cost of a pan, which evicts 512 KiB instead of 8 MiB.
- **This is the same defect the ADR was written to remove, and the transport study could not have caught it.** "Why these numbers" reasons about round trips, compressed sizes and an 8 MB per-frame upload budget — a bound on _rate_. The binding constraint on the 2D path is a bound on _residency_, and it is the one the rejected `Z > 1` gate would have hidden: a plate field never approaches it, a gigapixel lateral does immediately. A 2048² uint16 chunk is 8 MiB, which is also exactly one frame's upload budget, so the original yardstick condemns it too — the old default's indictment was 0.48 chunks per frame and this is 1.0.
- **The frustum argument does not transfer to 2D, and it did not need to.** ADR-0010's clearest statement — 64 admission slots buying a 256³ cube instead of 64 whole-brain planes — turns on a big chunk being mostly _off-screen_, which is a volumetric property. On a slide a large on-screen chunk wastes only its edges, so a request-count window would actually reward big chunks. The residency bound reaches the same conclusion by a different route, which is why the default survives: it is now justified by a measurement taken on the shape that threatened it, not by extrapolation from a volume.
- **The sharding rejection's reasoning is intact; its price was understated.** `lucida-store` still has no sharding support of any kind — zero occurrences of the word, and `parse_codec_chain` (`codec.rs`) still rejects any chain whose first codec is not `bytes`, which is exactly what a `sharding_indexed` array presents. So the trap the rejection names is real and shipping an opt-in flag today would still ship it. What changed is the alternative: Consequences called object count "irrelevant on local disk", and the fallback for a store that cannot afford 493k objects was assumed to be a mildly worse read. It is not. The fallback is a four-chunk viewport. The revisit trigger is unchanged — Lucida gaining `sharding_indexed` read support — but this is no longer an object-storage optimisation to reach for eventually.
- **Sharding is the only geometry that satisfies all three constraints, because the shard is the write unit and the chunk is the read unit.** 512² chunks inside 2048² shards give 31,156 objects (the shard count, matching the 8 MiB run), 8 MiB dask blocks and write objects (the unit that made that run finish), and a 512 KiB read unit (121 atlas slots). Measured on a 4096² × 2ch synthetic through `ZarrmonyWriter`: 512² unsharded wrote 130 objects in 0.42 s, 512²-in-2048² wrote 10 in 0.11 s, 2048² unsharded wrote 10 in 0.15 s. The two numbers that looked like a trade-off — 8 MiB for the writer, 512 KiB for the viewer — are two levels of one store.
- **Three implementation facts, recorded so the eventual field is not mis-plumbed** (tracked in issue #117 and acted on in the [follow-up below](#follow-up-issue-117)). `zarr.Array.chunks` on a sharded array returns the _inner_ chunk and `.shards` the outer, so `write_pyramid`'s rechunk to `dataset.chunks` would produce chunk-aligned blocks and read-modify-write every shard — correct, measurably slower, and 16× write amplification at scale. `da.from_zarr` likewise chunks on the inner grid, which would multiply `read_level`'s task count by the chunks-per-shard ratio and reintroduce #111's symptom on the pyramid's own read-back. And the `lock=True` in `write_pyramid`'s `da.store` becomes load-bearing for correctness rather than merely tidy, since unsynchronised concurrent writers to one shard lose updates.
- **What is not affected.** Sharding is a codec, so every consumer reaching pixels through `zarr.Array.__getitem__` is unchanged: full reads, subsets straddling both grids, `da.from_zarr`, and the `multiscales` metadata were all verified byte-identical against the unsharded store on zarr-python 3.1.6. The breakage is confined to consumers that parse the codec chain themselves — `lucida-store` — and to zarr-python 2 consumers, which already cannot read zarrmony output at all since it writes v3 exclusively.
- **`--chunk-target-bytes` now warns above `CHUNK_TARGET_WARN_BYTES` (2 MiB).** Raising it stays supported and stays the right answer for an archival store read in big sequential sweeps. It warns because its cost is not paid by the conversion in front of the user but by a viewer months later, and because the object-count problem it appears to solve is better solved by sharding — so the message names the residency figures and points at the alternative rather than merely discouraging the flag.

## Follow-up (issue #117)

Sharding ships, as `Geometry.shard_target_bytes` and `Geometry.shard_shape` (`--shard-target-bytes`, `--shard-shape`), both defaulting to `None` and both off unless a caller asks. This reverses the rejection in Considered Options above.

- **One premise flipped, not the analysis.** The rejection turns on there being no consumer, so a flag would be a trap and a "flag shipped is a flag supported". Both halves of that still hold — `lucida-store` is unchanged, and this slice is precisely the support cost the bullet priced. What changed is the ordering assumption underneath it: "revisit when Lucida gains `sharding_indexed` read support" made zarrmony's write side wait on a reader that has no reason to be built before there is something to read. The #113 measurements are what make waiting expensive rather than merely tidy — the fallback for a store that cannot afford its object count is a four-chunk viewport, and 512²-in-2048² is the only geometry that gives a viewer its 512 KiB read unit and a writer its 8 MiB write unit at once. So the store format goes first and the reader follows. Recorded plainly because it is a project-sequencing call, not a new technical finding: the trade-off the rejection describes is still the trade-off, and it is now being taken the other way.
- **The trap is answered at the point of use rather than by not shipping.** Turning sharding on prints a warning naming exactly who breaks and who does not: chunks stay individually readable and every zarr-python 3 consumer is unaffected, while a consumer that parses the codec chain itself sees `sharding_indexed` where it expects `bytes` and refuses the store. That is a one-line message where the alternative was an error reading as corruption.
- **Default off, so no conversion changes.** Output is byte-identical to a pre-#117 conversion unless shards are requested. `--shard-shape` and `--shard-target-bytes` are rejected together exactly as `--chunk-shape` and `--chunk-target-bytes` are; an explicit `shard_shape` that is not a whole multiple of the chunk on every axis fails by axis name before pixels move; and a `shard_target_bytes` below `chunk_target_bytes` is rejected at construction, since a shard holds whole chunks and so cannot be smaller than one.
- **The shard is planned by the same world-cubic rule as the chunk, over whole-chunk multiples.** `plan_shard_shape` searches per-axis doublings of the chunk length, scored by the identical `(voxels, cubeness)` key `plan_chunk_shape` uses — the two now share `_best_spatial_combo` — so a shard is the most nearly cubic-in-micrometres block of whole chunks that fits `shard_target_bytes`. T and C are pinned to the chunk's value: a shard spanning channels would make a single-channel read pull every channel's bytes off the wire.
- **`DEFAULT_SHARD_TARGET_BYTES` is 8 MiB, and that is a bare-flag default rather than a field default.** It is the write unit that took the whole-slide scene from a projected nine days to 3 h 02 m, and it holds 16 chunks of the 512 KiB default. Note that the ADR's own illustration — "a 256³ shard holds 64 chunks of 64³" — does not survive contact with a byte target: 256³ uint16 is 32 MiB, four times the target, so on isotropic data the planner returns `128 × 128 × 256` — 16 chunks arranged 2 × 2 × 4, 8 MiB exactly. The 68× object reduction that figure implied is really 16× at these defaults. On the whole-slide scene that is a 512² chunk inside a 2048² shard, 369,600 level-0 objects down to 23,184, which is the count the 8 MiB run actually wrote.
- **Every level is sharded, including levels where the shard degenerates to the chunk.** A coarse level small enough that one chunk already exceeds the target gets `shard == chunk`, which is a legal `sharding_indexed` array with one chunk per shard and pure overhead. The alternative — drop sharding on levels that do not benefit — was rejected because it makes "can my consumer read this store?" a per-level question, and a consumer that opens level 0 fine and fails on level 4 is worse than one that fails immediately. Pinned in a test.
- **The three implementation facts from #113 are plumbed at one site.** All three write paths funnel through `writers/scene.py`, so `_write_grid(dataset)` — `dataset.shards or dataset.chunks` — is the single place that decides what a write covers. `read_level` chunks `da.from_zarr` on that grid rather than the inner one, `write_pyramid` rechunks the source to it, and `da.store(..., lock=True)` is now load-bearing for correctness rather than tidiness. `shard_shapes` joins `chunk_shapes` in the audit (`null` when off) and `config.geometry` gains the two new fields — additive, but audit schema **12**, because "how many objects is this store, and do I need `sharding_indexed` to open it?" is no longer inferable from `chunk_shapes`. Unlike #87's no-bump case, this one is a real record-shape change.
- **napari-ome-zarr reads a sharded store identically.** Verified end to end rather than argued from the codec spec: against plain and sharded stores written by `ZarrmonyWriter`, `napari_get_reader` returns a multiscale image layer with the same layer type, level count, per-level shapes, dtype, per-level checksums, deliberately shard-unaligned subset sums, metadata keys and scale. The only differences are `codecs` and `shards`, and the object count (46 → 10 on the test store). The same run confirms the sharded array's codec list is exactly `['sharding_indexed']` — the string `lucida-store`'s `parse_codec_chain` rejects — so the two halves of this follow-up were measured in one place.
- **Not re-measured at the time of writing; since measured.** The numbers above were the planner's arithmetic and a synthetic write, and the case for the 3 h 02 m transferring from 8 MiB _chunks_ to 8 MiB _shards_ rested on #113's finding that cost scales with the write unit rather than with bytes. That re-conversion has now run — see [the #124 follow-up](#follow-up-issue-124) below, which confirms it and corrects one prediction made here.

## Follow-up (issue #112)

The policy decides the output geometry; nothing told the _input_ about it. `write_pyramid` absorbed the difference with a `rechunk`, and on the whole-slide path that rechunk was always a split. Zarrmony now plans the write grid before it reads pixels and reopens the reader asking for tiles that nest in it, recording the answer as `config.reader_tile_size` (audit schema **13**).

- **Splitting and merging are not the same operation, and the cost gap is an order of magnitude.** On the reference scene `[1, 4, 1, 140757, 171855]` uint16: 1024² source tiles into a 512² write grid build **831,936** dask tasks against 92,736 source blocks (9.0×); 512²→512² builds 369,600 (1.0×); 1024²→2048² builds 115,920 (1.25×) and 512²→2048² builds 392,784 (1.06×). Merging costs one concat task per output block. Splitting costs a slice task per output block _plus_ re-reading each source block once per block it feeds. The consequence is unintuitive enough that it survived a runbook review: asking a reader for **larger** tiles produces a **larger** graph.
- **So the rule is divisibility, not equality.** "Align the reader tile to the chunk" is the strong form and it is not achievable — one reader has one `tile_size` and a file has many scenes. The weak form is sufficient: the tile must _divide_ the write grid and never exceed it. That is what makes a single per-file tile size a correct answer rather than a compromise.
- **The fix has to reach the reader; the writer cannot buy it back.** `rechunk` with `method="tasks"`, `balance=False`, `threshold=1` and `block_size_limit=2³⁰` all return the identical 831,936 — the split is inherent in the block boundaries, not in dask's cost model. And task count understates it, since the re-reads are I/O against the source rather than graph overhead.
- **The write grid is `dataset.shards or dataset.chunks`, which is the #117 trap one level up.** Deriving the tile from the chunk under sharding would leave every write assembling 16 tiles into one shard. `plan_write_grid` is the single function both the writer and the tile derivation ask, so the two cannot drift.
- **Across scenes, take the element-wise minimum — and exempt any axis whose grid spans its extent.** The minimum is provably split-free: a planned length is either a power of two or the extent itself (`_axis_candidates` clamps), so the smallest power of two divides every other, and a clamped length has no interior boundary to split. Without the exemption a 375-row `label` thumbnail would pin the whole file's tile to 375 and make the gigapixel scene straddle on every write — the original failure, reintroduced by the fix for it.
- **dtype is a per-scene input, not a per-file one.** Caught against the real VSI rather than in review: its four scenes are `uint8` RGB `label` and `macro` beside `>u2` `overview` and fluorescence, and `reader.dtype` reports whichever scene the reader is pointing at — scene 0, the `uint8` label. itemsize divides the byte target, so planning the slide at itemsize 1 gives a 724²-voxel budget and a `(512, 1024)` grid where the truth is `(512, 512)`. That is wrong in the one direction that matters: too small an itemsize plans too _large_ a tile, which the real grid then splits. On this file the cross-scene minimum happens to rescue it; on a single-scene `>u2` file it would not. `plan_reader_tile_size` takes one dtype per scene alongside one shape and one spacing list per scene.
- **Planning needs a reader and the reader needs the plan, but only apparently.** `plan_chunk_shape` pins T and C to 1, so the Y/X answer depends only on Z/Y/X extents, spacings and itemsize — all metadata. `_scene_planning_inputs` reads them without touching `xarray_dask_data`, then `convert()` reopens with the derived tile. The reopen costs a second metadata parse, which against a conversion measured in hours buys the whole difference above.
- **Scoped to the default `bioio` plugin, and never overriding a caller.** `tile_size` is that plugin's convention; other plugins are left alone, as is a caller who pinned one, as is a reader whose metadata will not support planning. A reopen that raises warns and continues — alignment is an optimisation, not a precondition.
- **`TileAlignmentWarning` is the backstop for the paths alignment cannot reach**, and it names the tile that would have worked, because deriving it by hand is the part users get wrong. Restricted to Z/Y/X: the planner pins C to 1 unconditionally, so a reader handing several channels per block always trips the general predicate, and no `tile_size` addresses it.
- **The recommendation this repo shipped was the worst available option.** README, ADR-0011 and the VSI runbook all said `tile_size=1024,1024` — the 9.0× row. All three now say `dask_tiles=true` alone. The runbook keeps a pinned `tile_size` in its pre-flight snippet only, where the point is proving the kwarg reaches the backend.
- **Re-measured on the whole-slide scene at stock defaults: 1.45×, and it is not enough.** The #113 follow-up's ~38 chunks/min was taken with unaligned tiles forcing a rechunk, which left open whether object count was the real cost. It is. A fresh run with the derived `[512, 512]` tile and **no `TileAlignmentWarning`** — source blocks nesting one-to-one in the write grid — sustains **55 chunks/min**, so level 0's 369,600 objects still take ~4.6 days and the pyramid ~6. Against the 8 MiB run's ~155/min that is 0.46 MiB/s versus 20.7 MiB/s, ~44×; and each object is 16× smaller yet takes 2.8× longer to write (1.09 s versus 0.39 s), at ~107 % CPU on a 192-core host. Per-object time rising as objects shrink is the signature of scheduler cost scaling superlinearly with graph size, not of byte throughput — which is why alignment could not fix it and why sharding, which shrinks the graph rather than the chunk, is the lever that does. This supersedes the ~38 chunks/min figure above and closes #113.

For the other side of the margin: an unsharded 512 KiB attempt on this same slide was started and killed with its own object rate projecting **32–41 h**, so the gap is roughly 10–13× and both ends of it are now measured on the same input rather than extrapolated from a 4096² synthetic.

The stores are **88 MB apart on 139 GiB**. The reasoning is sound in principle and simply does not bite at this ratio: zstd on 512 KiB of 16-bit microscopy still finds essentially all the redundancy it finds in 8 MiB. Recorded because the trade is better than this ADR claimed — a read unit 16× smaller for 1.6 % of wall-clock and nothing on disk. This bullet originally added that a 2D result on plane-tile chunks "does not transfer to a cubic chunk cutting across the correlated axis of a volume"; [Follow-up (issue #126)](#follow-up-issue-126) measures the volume and shows the caveat was aimed at the wrong mechanism.

This is the same `_axis_candidates` clamp that #112 relies on for split-freedom, showing up on the shard grid. Correct, and previously unrecorded.
- **#112's alignment holds at full scale under sharding, and that settles the `lock=True` concern.** `grep -c TileAlignmentWarning` over the whole log is **0**: `config.reader_tile_size` was derived as `[2048, 2048]`, exactly the level-0 write grid, so no axis offends and `plan_write_grid` did its job as the single answer both sides ask. The read-modify-write hazard named in #113's implementation bullets did not materialise — the filesystem reported **149,233,246,208 B written against 149,161,908,098 B stored, a ratio of 1.0005**. Blocks map 1:1 to shards on the real write path, not only on the synthetic.
- **The cost of sharding is CPU and resident set, not elapsed time.** +19 % CPU is compression overhead — 493,484 blocks of 512 KiB compressed instead of 31,156 of 8 MiB, at the 2.8× per-object cost #113 measured — and it parallelises, which is why it does not appear in the wall-clock. +24 % RSS is the level-by-level writer of #111 holding a 2048²-aligned working set instead of an 8 MiB one. Both are worth naming for anyone sizing a host: the sharded path wants headroom, not more hours.
- **napari resolves the store at slide scale, on demand, over a network mount.** Zooming from whole-slide to level 0 stepped the status-bar level index `8 → 7 → 6 → 5 → 4 → 3 → 2 → 1 → 0`, monotonic with zoom, with level 0 rendering — so a 512 KiB chunk is being range-read out of an 8 MiB shard object at every level. The coordinate readout held still across all nine switches while the array changed shape by 512×, which is an end-to-end check that the `coordinateTransformations` agree across the pyramid. It opened at level 8 rather than 9, the shallowest level covering the viewport.
- **`scripts/verify_geometry.py` is worse than "the count is wrong".** #117 flagged that it predicts object count from the chunk grid. Run against a real sharded store, **the report never mentions sharding at all** — no shard shape in the checks, no shard column in the levels table, nothing in the measurements. It reports the inner chunk as if it were the store's only chunking and prints `Chunk objects (from the level grids): 493,484`, the _unsharded_ prediction computed live from a sharded store, and every check passes. `--no-object-count` suppresses the false failure but not the misrepresentation. Since the report is the artifact people keep, the fix's scope is "the report states the shard shape", not just "the count is right". Tracked on #129.

## Follow-up (issue #122)

The planner has always known the exact object count — it resolves every level's shape and every level's chunk shape before a byte moves — and it never said so. A gigapixel 2D scene at the 512 KiB default plans 493,484 objects and runs for about six days ([#113](#follow-up-issue-113)); the user found that out by watching it not finish. `count_storage_objects` now totals the write grid over a pyramid, and an unsharded scene above `STORAGE_OBJECT_WARN_COUNT` raises `ObjectCountWarning` at plan time.

- **The threshold is 100,000 objects for one scene's whole pyramid, and it is the gap between the only two counts this project has measured.** The 512²-in-2048² acceptance run wrote **31,156** objects in 3 h 04 m and was fine ([#124](#follow-up-issue-124)); the same scene unsharded plans **493,484** and was not. 100,000 is ~3× above the comfortable count and ~5× below the intolerable one, so it separates them without sitting on either. Both numbers are re-derived from the planners in a test rather than quoted, since the threshold means nothing except relative to them.
- **It is a warning, and the message has to name the catch or it is worse than silence.** The lever is `--shard-target-bytes`, which packs the same chunks into larger objects and changes nothing a reader sees — except that a sharded store needs `sharding_indexed` support to open, and `lucida-store` still has none. So the message carries the projected count, the scene it is about, the ~6 days, the flag, the count the flag would give, and the readability catch. Dropping the last clause would trade a slow conversion for a store the user's viewer cannot open at all, which is the trade the [#117 reversal](#follow-up-issue-117) took deliberately and with the warning attached.
- **Nothing is refused and no default moves.** The run is correct and the count may be exactly what the user wants; the `warnings` filters are the override, so there is no suppression flag and no `Geometry` field — a knob that changes no output does not belong in the audit record.
- **Per scene, not per store.** The check lives in `write_scene`, the one function per-scene, bf2raw and plate output all funnel through, at the point where the chunk and shard shapes are resolved and the writer has not been constructed. The consequence is that a plate whose fields are individually tiny but which totals ~100k objects across the store — the case Consequences already names — does not warn. Known gap, recorded rather than papered over.
- **The arithmetic is a shared helper because the acceptance tool needs the same number.** `scripts/verify_geometry.py` predicts object count off the chunk grid, which is the wrong grid on a sharded store — it reported `493,484` against a store holding 31,156 shards and passed every check ([#124](#follow-up-issue-124), tracked on #129). `count_storage_objects` takes one write grid per level, so both callers reach the same figure by construction. It returns an **upper bound**, per the volumetric run: zarr writes no all-fill object, so assert `objects <= count`, never equality.
