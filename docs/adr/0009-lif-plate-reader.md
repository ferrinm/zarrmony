# Leica LIF plate reader — detection and filter semantics

**Status:** Accepted (2026-08-10).

The built-in `bioio-lif` reader detects HCS plate acquisitions by walking the `LMSDataContainer` XML tree — not by parsing the derived `{plate}/{row}/{col}` scene-name pattern — and, when the file describes exactly one plate, sets `layout_hint="plate"` and populates `plate_layout` per [ADR-0004](./0004-plate-output-design.md). Multi-plate LIFs surface every plate template through an `available_plates` list; a `--plate NAME` CLI selector (and matching `plate=` reader kwarg) filters `reader.scenes` to a single plate before conversion. `--plate` is required only when the LIF is ambiguous (multi-plate); a single-plate LIF resolves without it. Column strings are width-2 zero-padded (`"01".."12"`) and row letters are single uppercase (`"A".."H"`) regardless of what the LIF XML happens to store, matching `zarrmony-phenix`. Row/column lists carry every well the LIF plate template declares even when only a subset was imaged (sparse-plate semantics per ADR-0004). Under plate mode the LIF mosaic-FOV cascade (stage-stitch → grid-stitch → bioio-lif fallback) runs unchanged; users needing per-tile output for a plate FOV convert as flat (`--layout per-scene`) because `lif_mosaic="per-tile"` is incompatible with the "one FOV = one image" plate contract (ADR-0005). This ADR is decisions-only; implementation ships in #81 (single-plate tracer bullet) and #82 (multi-plate + `--plate`).

## Considered Options

- **Parse the `{plate}/{row}/{col}` scene-name pattern instead of the XML.** Rejected. Scene names are a human-readable projection of the XML plate template; they are not the template. LAS X operators routinely rename scenes, drop the plate-name prefix on export, or use non-standard delimiters (spaces, colons, mixed padding), all of which corrupt the pattern without corrupting the underlying `LMSDataContainer` structure. Round-tripping structured data through a string format is the exact failure mode ADR-0004 rejected for the Protocol boundary; repeating it inside the reader would push the same fragility one layer down. The XML walk is authoritative; the scene-name pattern may be used as a low-cost sanity check ("does the row I parsed from XML also appear as the middle path segment of this scene's name?") but never as the primary source. A single-place-to-parse-plate-shape decision keeps the maintenance surface small: bioio-lif's own `scene_root` fast path already returns the well `<Element>` for plate scenes and raises for non-plate ones (see `metadata/_lif_scene.py`), so the walker has one clean discriminator.
- **Emit a plate per detected template automatically, silently picking the first when multiple exist.** Rejected. ADR-0004 locks `plate_layout` as a single `PlateLayout`, not a list, and locks single-plate-per-`convert()` at the Protocol shape. A LIF holding two plates (the user's real 30 GB `PFF-HEK293-seeding-07172026.lif` packs `BFP-SNCA-WT` and `BFP-SNCA-A53T` into one file) is a common enough shape to warrant an explicit disambiguator, not a silent policy. Silently picking one would produce a partial plate.zarr with no signal that the other plate was ever there — the same failure mode the "silent bad stitch" one in ADR-0005 exists to prevent.
- **Always require `--plate NAME` on any plate-shaped LIF.** Rejected. Correct for correctness's sake — one edge case fewer — but wrong for ergonomics: every existing single-plate LIF user would have to look up the plate name in `inspect` output and pass it back on every `convert` invocation, even when the reader has zero ambiguity. That is precisely the "smart default + user override" anti-pattern locked in `feedback_configurability`: the smart default handles the unambiguous case; the override handles the ambiguous one. The single-plate path with `--plate` accepted (and validated to match) covers users who want explicit belt-and-suspenders; the required-when-ambiguous rule covers the multi-plate case with an actionable error.
- **Multi-plate LIF without `--plate` silently converts every plate into sibling `out/<basename>__<plate_name>.plate.zarr` stores.** Rejected. A one-liner that produces N stores instead of one violates the "one convert() call, one output path" invariant users rely on for pipelining (Snakemake, CI, cloud batch jobs — the `out/` directory is a single deliverable). It also forces zarrmony to invent a naming scheme for the sibling stores that would conflict with the user's own naming convention. The `--plate NAME` selector + explicit re-invocation gives the user full control over both plate ordering and output-store naming with no policy on our part.
- **Under plate mode, refuse to fall back to bioio-lif's auto-stitcher for mosaic FOVs (force `lif_mosaic="per-tile"` or raise).** Rejected. Two blockers: (1) `lif_mosaic="per-tile"` is already incompatible with plate layout by ADR-0005 (a plate FOV is one image by spec; per-tile produces N sub-stores per FOV that the plate spec cannot express) — `convert()` raises `LayoutMismatchError` before the writer is even called. (2) Forcing the cascade to refuse the bioio-lif fallback would break every plate LIF whose per-tile `<Tile>` layout metadata is missing or malformed (the same "no XML surface, no reassembly possible" case that drops the flat-scene path to bioio-lif today). The flat-mode cascade already fires `MosaicStitchingWarning` naming the pathologies and the escape hatch; the same warning firing per plate FOV is the right signal. Users who need pixel-correct tile output for a plate FOV convert as flat (`--layout per-scene` on a plate reader emits `LayoutDowngradeWarning` and writes flat scenes; `lif_mosaic="per-tile"` then applies as normal) — that route is documented as the plate-side escape hatch. Refusing the fallback would be a hard-error breaking change with no graceful path for existing plate mosaic LIFs.
- **Preserve LIF's own column-padding and row-letter case verbatim (no normalization).** Rejected. LIF exports have been observed with both zero-padded (`"01"`) and unpadded (`"1"`) columns, and with row letters in either case, depending on LAS X version and template author. Passing that variance through would make the on-disk `<plate>/<row>/<col>/` paths differ across two files that describe the same plate shape — the exact reason ADR-0004's writer treats the reader's row/column strings as canonical. Normalizing at the reader boundary (width-2 zero-padded columns, single uppercase row letters — the `zarrmony-phenix` convention) gives every plate reader the same on-disk shape for the same plate. The normalization is a pure formatting decision (`f"{int(col):02d}"`, `row.upper()`); the underlying vendor label survives in the audit's per-field record if a downstream consumer needs the original.
- **Support width-3+ column padding (e.g. `"001"`) for future 384/1536-well or non-standard plate templates.** Rejected for this ADR. OME-NGFF plate examples and every existing pilot fixture use width-2 padding; 1536-well plates (48 columns) still fit width-2. If a real user acquires on a >99-column instrument the padding decision can be revisited in a follow-up — a width-3 shim is a five-line change and the ADR-0004 writer treats row/column strings as opaque. Committing to a wider default now would ship an on-disk shape divergent from `zarrmony-phenix` for zero present benefit.
- **Sparse-plate semantics: emit only the rows and columns that have at least one imaged FOV.** Rejected. ADR-0004 explicitly locks "the reader emits every row/column declared in the plate template even when only some are imaged" and treats the responsibility as reader-side. A LIF plate template records the full physical shape (e.g. the operator selected a 96-well plate template and imaged 12 wells); collapsing the row/column lists to only-imaged wells would (a) misrepresent the plate to plate-aware viewers that render an empty-well grid, and (b) diverge from the `zarrmony-phenix` shape for the same plate imaged sparsely, which defeats the point of a shared writer contract. Unobserved wells are simply absent from `plate_layout.fields`; the row/column lists carry the acquisition-template shape.
- **Support per-plate CLI selection by integer index (`--plate 0`, `--plate 1`) instead of by name.** Rejected. Plate order in the LIF XML tree is a function of LAS X's internal traversal, not user-visible acquisition order — the same file re-exported from LAS X can reorder plates. Index-based selection would silently pick a different plate across otherwise-identical files. Name-based selection is stable across LAS X exports because plate names are user-authored template identifiers. The error message on ambiguity lists names, not indices, for the same reason.
- **Lift plate-XML parsing into a standalone `metadata/lif_plate.py` module now.** Deferred. The extractor is worth factoring out (dependency-free, fail-closed XML walking mirrors `lif_tiles`/`lif_shading`), but the layering decision — module boundary, extractor return shape, whether the walker also emits `available_plates` for the multi-plate case or that lives in the plugin — is implementation, not policy. #81 lands the extractor in whichever module fits the tracer-bullet cleanly; a follow-up refactor can hoist it out if a second consumer (e.g. an external audit tool) materializes.

## Consequences

- **Source of truth is `LMSDataContainer` XML.** The reader walks the LIF XML tree (via the same `find_scene_xml` surface `_lif_scene.py` already establishes) to enumerate plate templates and, for each, the well/field structure. The `{plate}/{row}/{col}` scene-name pattern is not consumed as the primary source; when it is present and parseable it may be cross-checked against the XML-derived shape (mismatch fires a diagnostic warning — shape to be decided during #81 implementation), but the XML shape wins.
- **`_MosaicAwareLifReader` (or its successor) gains an `available_plates: list[str]` attribute** enumerating every plate template found in the LIF XML in first-encountered order. Empty list means the file is not plate-shaped (flat LIF, existing behavior preserved). Single-element list means unambiguous plate mode. Multi-element list requires `--plate NAME` selection.
- **`layout_hint = "plate"` fires when exactly one plate is selected** — either because `available_plates` has length 1 (single-plate LIF, `--plate` optional) or because the user's `--plate NAME` selection resolved against a multi-plate LIF. When `available_plates` has length ≥ 2 and no `--plate` was passed, the reader raises with an actionable error naming every available plate and suggesting `--plate NAME`; `layout_hint` stays at its default (`"flat"`) on the raise path so a caught exception doesn't leave the reader in a half-plate state.
- **`plate_layout.rows` carries every physical row and `plate_layout.columns` carries every physical column** from the LIF plate template, formatted as single uppercase letters and width-2 zero-padded numeric strings respectively (`["A", "B", ..., "H"]`, `["01", "02", ..., "12"]`). Wells not imaged are absent from `plate_layout.fields` but present in `rows`/`columns` — matching ADR-0004's sparse-plate contract and `zarrmony-phenix`'s output shape for the same physical plate.
- **`plate_layout.plate_id` is populated from the LIF plate template's identifier** when the XML records one (ADR-0008 / #66 audit surface). When the template records only a human-readable name, `plate_id` is `None` and only `plate_layout.name` carries the label.
- **CLI grows a `--plate NAME` option** (implementation in #82). Not passed on a multi-plate LIF → actionable error naming available plates. Not passed on a single-plate LIF → silently resolves to the sole plate. Passed on a single-plate LIF → validates that NAME matches the plate's name (mismatch raises with both the requested and available names). Passed on a multi-plate LIF with unknown NAME → raises with the available names. The CLI option threads through to the reader via the `reader_kwargs` surface #79 already established (`plate=` kwarg).
- **Mosaic-FOV cascade under plate mode runs unchanged.** The `lif_mosaic="auto-stitch"` cascade (stage-stitch → grid-stitch → bioio-lif fallback) applies to plate FOVs identically to flat scenes; per-FOV `MosaicStitchingWarning` fires when the fallback lands. `lif_mosaic="per-tile"` continues to raise `LayoutMismatchError` under plate mode (ADR-0005 unchanged) with the message pointing at `--layout per-scene` as the escape hatch. `lif_mosaic="stage-stitch"` under plate mode continues to raise per ADR-0005. `lif_mosaic="grid-stitch"` under plate mode continues to work per ADR-0004 §Follow-up + `writers/plate.py`.
- **Column-padding and row-case normalization happen at the reader boundary.** The reader normalizes XML-sourced strings to canonical form before populating `PlateLayout`; the plate writer treats the strings as opaque (as it already does). Two LIF files describing the same 96-well plate produce the same on-disk `<plate>/<row>/<col>/` shape regardless of how LAS X happened to serialize the row/column labels in either file. The audit's per-field record preserves the original vendor label so a downstream consumer can round-trip if needed.
- **Non-plate LIF regression path.** LIF files whose XML has no plate template continue to open as flat readers (`layout_hint = "flat"`, `plate_layout = None`) with zero behavior change — existing single-scene and multi-scene confocal LIF conversions are untouched by this ADR. The `available_plates` attribute reads `[]` for these files.
- **`inspect()` output additively grows a `plate` block for plate-shaped LIFs** (single-plate) and a `plates` block listing every available plate name (multi-plate). Existing flat-LIF `inspect()` output is unchanged; existing plate-shaped inspect output for `zarrmony-phenix` is unchanged. Format details are ADR-0004's `summarize_plate_layout` surface, reused verbatim.
- **No `audit_schema_version` bump.** The reader consumes ADR-0004's existing `plate_layout` Protocol surface and ADR-0008's existing `plate_id` audit surface; no new audit keys, no new warning classes, no new writer branches. This ADR is purely a reader-side detection + filter policy.
- **SemVer.** No release ships from this ADR alone. #81's tracer bullet lands as a minor bump (new plate-shaped output from a reader that previously emitted flat scenes changes on-disk behavior for plate-shaped LIFs); #82 lands as another minor bump (new CLI surface). Both slices land under the current `[Unreleased]` block and the CHANGELOG migration note documents the shape change for existing LIF users whose files happen to be plate-shaped (they will start getting plate.zarr instead of per-scene stores under the default `--layout auto`).
