# Plate output design

Zarrmony grows a third writer layout, `layout="plate"`, that emits an OME-NGFF 0.5 high-content-screening (HCS) plate store. The Reader Protocol gains a `plate_layout: PlateLayout | None` attribute carrying the structured plate shape (rows, columns, wells, acquisitions, per-FOV coordinates); plate-shaped readers populate it. The default `layout="auto"` reads `reader.layout_hint` and dispatches: `"flat"` → `per-scene`, `"plate"` → `plate`. ADR-0002's reservation of `layout_hint` is now consumed.

## Considered Options

- **Reader-driven dispatch only (no user override).** ADR-0002 implied the writer simply reads `layout_hint` and emits the matching shape — no user `layout=` argument needed. Rejected: the established "smart default + user override" pattern (locked decision #4-ish in `notes.org`) wants the user to be able to force flat output from a plate-shaped reader for debugging or for non-plate-aware downstream tools. `layout="auto"` honors both: reader hint by default, explicit override available.
- **Parse plate coordinates from scene-name strings.** Keep `layout_hint` as the only Protocol surface; have plate-shaped readers encode "B04-f02-a1" in `scenes`, and let zarrmony parse it. Rejected: round-tripping structured data through string formats is fragile (delimiter conflicts, acquisition names like "DAPI baseline" don't slug cleanly), couples zarrmony to a specific naming convention, and loses information for sparse plates (the spec requires every physical row/column be listed even when not imaged — only the reader knows which they are). A structured `PlateLayout` dataclass is one Protocol addition for unambiguous semantics.
- **Multi-acquisition and multi-plate support in v1.** The spec allows a plate's `acquisitions` list to have N entries, and a single Phenix session can in principle contain multiple `Plate` records. Rejected for v1: pilot data is single-acquisition, single-plate; building Protocol surface, writer branches, and well-metadata variants for use cases without test fixtures violates the tracer-bullet pattern. The Protocol carries `acquisitions: list[Acquisition]` and `acquisition_id: int | None` from day one (so the field reservation matches ADR-0002's pattern), but the writer asserts `len(acquisitions) <= 1` and ignores `acquisition_id`. Multi-acquisition gets a follow-up ADR when it ships.
- **New pixel-writing path inside `writers/plate.py`.** The plate writer could own the full pipeline (pyramid build, OMEZarrWriter init, dask write) with optimizations like shared chunk shapes and parallel FOV writes. Rejected: a plate FOV is structurally identical to a scene in `per-scene` / `bf2raw` layouts — same multiscales, same OME-Zarr v0.5 image. Reusing `writers.scene.write_scene` per FOV keeps one pixel/metadata path under maintenance; optimizations (parallel writes, shared rechunking) wait until profiling against a real Phenix-sized plate justifies them.
- **Per-FOV `OME/METADATA.ome.xml` sidecars (matching per-scene mode).** Plate FOVs could each carry an `OME/METADATA.ome.xml` mirroring how per-scene stores are self-describing. Rejected: plate FOVs are not standalone OME-Zarrs — they are leaves of a plate, and the unit of provenance is the plate. Writing 864 OME-XML files into a 96-well × 9-field plate for zero downstream consumer is bloat. The combined `OME/METADATA.ome.xml` lives at the plate root only; the bf2raw writer's `build_combined_ome_xml` is reused for it.
- **Emit the `bioformats2raw.layout` marker on plate stores.** Spec section 228 explicitly permits the combination, and bioformats2raw itself does this. Rejected: the marker is a transitional bridge for tools that pre-date OME-NGFF plate; the locked v0.1 design notes already classify `bioformats2raw.layout` as "transitional" / a deprecation track. Modern plate readers (napari-ome-zarr, MoBIE, ome-zarr-py) consume the `plate` key directly. Adding the marker would also force fabricating an `OME/series` list against row groups (`A/`, `B/`) that don't fit bf2raw's numbered-subgroup model. One layout, one marker — predictable.
- **Three-level metadata inheritance (root → well → FOV) via combined `per_scene_metadata` + `per_well_metadata`.** Rejected for v1: the third level (per-FOV) requires an `attrs.zarrmony.user_metadata` slot inside every FOV `zarr.json`, and per-FOV metadata variation is rare in HCS workflows (treatments, controls, concentrations vary per well). Plate mode rejects `per_scene_metadata` outright; `per_well_metadata` is the single override layer. Per-FOV metadata can land in v2 under its own parameter without breaking v1.
- **`inspect()` returns a different shape for plate-shaped readers.** Switching `{"scenes": [...]}` to `{"plate_layout": ..., "fields": [...]}` based on `layout_hint` would force callers to dispatch on shape. Rejected: additive (`plate_layout` appears alongside the existing `scenes` list when present) keeps existing flat-caller code untouched and gives plate users the headline summary they need pre-conversion.

## Consequences

- **`audit_schema_version` bumps to `3`.** Plate audit records use `fields: [...]` (not `per_scene`) and gain a top-level `plate` key (sibling to `config`) carrying the resolved plate structure. Existing flat-layout audits continue to use `per_scene`. Audit consumers (Tenaya, Lucida, anything else reading `attrs.zarrmony`) switch on `audit.layout` to pick the right key. The CHANGELOG migration note documents the discriminator.
- **New error and warning classes in `errors.py`.** `LayoutMismatchError` (raised when `layout="plate"` is passed against a flat reader), `LayoutDowngradeWarning` (emitted when a plate-shaped reader is written as `per-scene` or `bf2raw`, dropping plate metadata; also emitted when scenes in `reader.scenes` are not referenced by any `PlateField`), `PlateLayoutError` (raised by writer-side `PlateLayout` validation before any pixels are written).
- **Reader Protocol has one new attribute and three new dataclasses.** `ReaderProtocol.plate_layout: PlateLayout | None`. New module exporting `Acquisition`, `PlateField`, `PlateLayout`. The `writing-a-reader-plugin.md` guide grows a "Writing a plate-shaped reader" section.
- **Per-well metadata persists to two locations.** Each well group's `<plate>/<row>/<col>/zarr.json#attrs.zarrmony.user_metadata` carries the well-level override; the audit's `plate.wells[i]` block also records it. Two-level inheritance (root → well) is sufficient for v1 HCS workflows; per-FOV is deferred. Users can stuff per-FOV variation into a free-form blob via `UserMetadata.extra="allow"` as a workaround.
- **`layout="auto"` becomes the new default `convert()` argument value.** Existing flat-reader callers see no behavior change (`auto` resolves to `per-scene`). The CLI default flips from `--layout per-scene` to `--layout auto`. CHANGELOG flags this as a behavior change for v0.3 with the same kind of migration note v0.2 carried for the per-scene flip.
- **Single-plate-per-`convert()` is enforced by Protocol shape.** `plate_layout` is a single `PlateLayout`, not a list. Adapters whose input contains multiple physical plates either set `layout_hint="flat"` (and let users get flat-scenes output) or expose only the first plate with a warning; either way the choice is the adapter's, not zarrmony's.
- **Sparse-plate semantics depend on the reader.** Zarrmony validates internal consistency (`PlateField.row` is in `PlateLayout.rows`, no duplicate well paths, etc.) but does not infer "missing" rows or columns — it has no plate-format knowledge. The Phenix adapter is responsible for emitting `rows=["A".."H"]` and `columns=["01".."12"]` for a sparse-imaged 96-well plate, even when only six wells are imaged.
