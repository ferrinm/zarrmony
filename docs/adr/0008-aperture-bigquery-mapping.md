# Aperture BigQuery ↔ zarrmony field-mapping contract

Land the mapping between zarrmony's `attrs.zarrmony` audit block and the Aperture `zarrmony_metadata` BigQuery table (schema at [`iac-aperture/deploy/arch/bigquery.tf`](https://github.com/calico/iac-aperture/blob/main/deploy/arch/bigquery.tf)). For every BQ column the reference doc tags one of three owners — `zarrmony-supplied` (source path in the audit + reader that populates it), `user-supplied` (ingest form, zarrmony never attempts extraction), or `derived` (ingest computes from a zarrmony field or from the transfer manifest). Column-by-column enumeration and the per-format extractability matrix live in [`docs/references/aperture-bigquery-mapping.md`](../references/aperture-bigquery-mapping.md); this ADR fixes the audit-shape decisions the follow-on extractor slices (#61–#66) write into so the readers and the ingest team can build in parallel against one contract. Amended by [Follow-up (issue #116)](#follow-up-issue-116), which makes the `input` block say when the path the user named is an index rather than the data.

## Considered Options

- **Per-scene placement for acquisition metadata (`acquisition_date`, `microscope`, `microscope_serial`, `imaging_method`).** Accepted. Every scene record grows an `acquisition: {date?, microscope?, microscope_serial?, imaging_method?}` sub-block with every key optional. `imaging_method` is `list[str]` (matches the BQ `imaging_method` `REPEATED STRING` shape); a single-modality confocal scene emits `["confocal"]` and a rare multi-modal scene emits `["confocal", "widefield_fluorescence"]`. Ingest unions across scenes when writing the per-file BQ row. Values are duplicated across scenes when the source file records them once at the file level — the common case for a single-session LIF/CZI/ND2. Consumers read one path regardless of layout (`per_scene[i].acquisition` for flat, `fields[i].acquisition` for plate); no layout dispatch, no "read root-level first, override per scene" branch to get wrong. File-level variation (a multi-session file concatenating two acquisitions) survives without a schema change, and plate mode has no natural file-level home for these fields — a per-field placement lets one shape cover both layouts.

- **File-level `acquisition` block with per-scene as override.** Rejected. Saves ~40 bytes per scene in the constant-across-scenes case (the common case) but forces every consumer to walk two paths and answer "file says X, scene says Y — which wins?" somewhere. The per-scene rule is boring and the duplication cost is trivial at pilot audit sizes; the extra shape buys nothing a BQ ingest layer would notice.

- **Channel identity shape: `per_scene[i].channels: list[dict]`.** Accepted. Each channel record is `{index, name, dye?, fluor?, excitation_nm?, emission_low_nm?, emission_high_nm?, color?, lut_name?}` — the exact surface `metadata.lif_channels.extract_channels` already returns for LIF (which is thrown away today after building the omero block), plus `color` (hex6, already computed for omero rendering under [ADR-0007](0007-emission-band-channel-colors.md)). The LIF path persists what `extract_channels` produces verbatim; the CZI/ND2/default paths project `reader.ome_metadata.images[0].pixels.channels` into the same shape, populating `{name, color}` at minimum and any of `dye/fluor/excitation_nm/emission_low_nm/emission_high_nm` that bioio's OME surface exposes. Missing keys are omitted rather than emitted as `null` so downstream can distinguish "reader didn't extract this field" from "reader tried and got nothing." This is the audit surface the ingest team reads for `channel_fluorophores` (semicolon-joined `fluor`, fallback `dye`) and — occasionally, per the provenance rule below — for `channel_targets`.

- **Emit missing per-channel keys as `null` instead of omitting them.** Rejected. `null` and "key absent" carry the same downstream semantics for a `channel_fluorophores` string-join (both skip), but a future field like `excitation_nm` needs the distinction between "reader has no wavelength surface at all" (key absent) and "reader has the surface but this channel's laser is undocumented" (`null`). Omit-on-absent lets the follow-on nullable-value case grow without breaking existing consumers who already treat "missing key" as "not extracted."

- **`ome_ngff_version` under a new top-level `output` block.** Accepted. `output: {ome_ngff_version: "0.5"}` sits alongside `input` and `config` at the audit root. NGFF version is a writer emission, not a caller argument (`config` verbatim carries `convert()` kwargs and NGFF version isn't one) and not an input-file property (`input` records source-file forensics). An `output` block is the extensible home for later output-metadata (output URI post-move, output-store checksum, on-disk byte count) that the pilot doesn't need today but that BQ columns like `uri_ome_zarr` will want a first-class source for once the ingest layer isn't the sole author of the URI.

- **`ome_ngff_version` under `config`.** Rejected. `config` is a verbatim echo of `convert()` kwargs (`layout, pyramid_min_size, chunk_shape, channel_colors, contrast_percentile, force, checksum, validate, lif_mosaic`). Adding a computed-by-writer field there muddies the block's semantics and forces every audit consumer to know which `config` keys are caller-supplied inputs and which are writer emissions. Separate block, no ambiguity.

- **`channel_targets` populated primarily by zarrmony.** Rejected. Target identity (RNAscope probe genes, antibody clone targets) is biology metadata the operator holds; the channel name in the source file is a rendering label. In practice Leica RNAscope files sometimes carry the target gene as the channel name (`"Vegfa"`) and sometimes carry a generic dye label (`"Cy3"`) — the ingest form is the only reliable source. Zarrmony's obligation stops at surfacing whatever channel identity the file records in `per_scene[i].channels[i].name`; the ingest layer MAY consult that field as a hint when the user leaves the form blank, but the reference doc flags this explicitly as "user-supplied (zarrmony-hint)" so downstream doesn't over-trust the extraction. Auto-populating `channel_targets` from `name` in every file would silently mislabel generic acquisitions with dye names as targets.

- **Extract `plate_id` and `well_id` in this ADR.** Rejected — scope kept out. Issue #66 owns the plate identity surface (`plate.plate_id` and per-field `well_id`) because it lands with test-fixture verification against Phenix output. This ADR names #66's outputs as the source for the BQ `plate_id` / `well_id` columns and points at them from the reference doc; #66's audit shape stays in its own scope.

- **Bundle a machine-readable `schema.json` alongside the reference doc.** Deferred. The Aperture ingest reader is Python and today parses `attrs.zarrmony` in application code; a JSON Schema would be the right escape hatch once a second consumer arrives (a validator, a TypeScript client), but shipping one now creates a second document to keep in sync with the reference table for zero additional consumer. Land the human-readable table; add the manifest if/when a second consumer needs machine-readable field descriptions.

- **Bump `audit_schema_version` in this ADR.** Deferred. The audit changes are additive — `per_scene[i].acquisition`, `per_scene[i].channels`, top-level `output` — and older consumers ignore unknown keys. The bump attaches naturally to the first implementation slice that actually writes these fields (whichever of #61–65 lands first). This ADR names the target: **v8**, bumped by the first extractor slice to merge.

## Consequences

- **New reference doc: `docs/references/aperture-bigquery-mapping.md`.** Enumerates every column in `zarrmony_metadata` with an owner tag + source path, plus the per-format extractability matrix. First reference doc in the repo (the directory is new); establishes the convention that cross-team contract material lives under `docs/references/`. Regenerated by hand when `iac-aperture/deploy/arch/bigquery.tf` gains or drops columns — the file header names the source of truth.

- **Audit schema v8 (target) grows three additive surfaces.** `per_scene[i].acquisition: {date?, microscope?, microscope_serial?, imaging_method?: list[str]}` — every key optional, block omitted entirely when the reader extracted nothing. `per_scene[i].channels: list[dict]` — one record per channel with `{index, name, dye?, fluor?, excitation_nm?, emission_low_nm?, emission_high_nm?, color?, lut_name?}`, each key present only when populated. Top-level `output: {ome_ngff_version: "0.5"}` — one key today, extensible. Plate-mode `fields[i]` carry the same `acquisition` and `channels` surfaces; the flat-vs-plate discriminator remains `audit.layout` per [ADR-0004](0004-plate-output-design.md).

- **Follow-on slices are the extractors; this ADR is the wiring shape.** #61 persists LIF's already-extracted channel identity into `per_scene[i].channels`. #62 adds LIF acquisition metadata (`date`, `microscope`, `microscope_serial`, `imaging_method`) from the `HardwareSetting`/`ATLConfocalSettingDefinition` XML. #63/64/65 add the same acquisition+channels surface for CZI, ND2, and default (OME-TIFF + other bioio plugins) reader paths using `reader.ome_metadata`. #66 lands plate identity (`plate.plate_id`, `fields[i].well_id`). Each slice ships with per-format tests; this ADR is what they read to agree on the audit-side key names.

- **`channel_targets` provenance rule.** BigQuery `channel_targets` is populated by the ingest form. Zarrmony's contribution is the per-channel `name` field surfaced in `per_scene[i].channels[i].name` — the ingest layer MAY consult it as a fallback when the user's `channel_targets` field is blank, but the reference doc flags this explicitly ("user-supplied, zarrmony-hint") so consumers know not to over-trust it. Leica RNAscope files where the operator wrote the target gene into the channel label are the case this hint serves; generic files with channel names like `"DAPI" / "AF647"` are not a legitimate target list, and auto-propagation would silently mislabel them.

- **`microscope` vs `microscope_name` disambiguation.** The BQ schema distinguishes `microscope` (brand/model — `"Leica SP8"`) from `microscope_name` (Calico-internal instance name — `"Snouty"`). Zarrmony populates `microscope` from the acquisition-file metadata; `microscope_name` is user-supplied per Calico's instrument-naming convention (no source-file surface for the internal name). The reference doc calls this out because "microscope" alone is ambiguous.

- **Per-format extractability matrix names today's state as `partial pending #61–65`.** No `zarrmony-supplied` column is `✓` in the shipped matrix for anything other than `ome_ngff_version` (writer constant), `micrograph_name` (`scene_name` is already in the audit today), and — after #61 — LIF's `channel_fluorophores`. Every acquisition-metadata cell (`acquisition_date`, `imaging_method`, `microscope`) is `partial` in every reader column, with a one-line note naming the follow-on issue. This is the honest starting picture and gives the ingest team the coverage timeline they need to plan around.

- **Documentation-only slice — no code, no version bump, no CHANGELOG entry.** The follow-on slices bump `audit_schema_version`, extend the writer, and add CHANGELOG entries; this ADR is the contract they're built against. Merging is safe against any pilot deployment.

- **The [ADR-0004](0004-plate-output-design.md) discriminator (`layout` → `per_scene | fields`) is preserved.** BQ consumers reading a plate audit find channel and acquisition metadata under `fields[i]` (not `per_scene[i]`), and a flat audit under `per_scene[i]`. The reference doc's audit-path column names the flat variant only, with a header note that plate audits swap `per_scene` → `fields` — one place to look for the branching rule.

- **The BQ `micrograph_name` column was renamed to `acquisition_name` in the July 2026 schema update.** The audit source path is unchanged (`per_scene[i].scene_name`); only the BQ column name changed. The reference doc uses the current BQ name.

- **Adjacent BQ tables `zarrmony_study_submission` and `zarrmony_study_status_tracker` are out of scope.** Neither is populated by zarrmony. `zarrmony_study_submission` is the submission-time form snapshot; three of its columns (`microscope`, `imaging_method`, `microscope_name`) also appear in `zarrmony_metadata` — the submission table carries what the user declared at form time and the metadata table carries what zarrmony extracted at conversion time. Ingest resolves the merge (typical rule: prefer zarrmony's extraction where present, fall back to the submission-declared value). `zarrmony_study_status_tracker` is server-managed pipeline state. Both tables are enumerated in the reference doc for context.

- **The audit carries several fields not currently consumed by any BQ column** — `per_scene[i].objective`, `per_scene[i].physical_pixel_size`, `per_scene[i].mosaic.*`, `per_scene[i].contrast.per_channel`, `attrs.zarrmony.reader_plugin`, `attrs.zarrmony.input.{size_bytes, mtime_iso, sha256}`. The reference doc catalogs these under an "additional zarrmony surface not currently consumed" section so the ingest team knows what's available if a future BQ column asks for them; no work on the zarrmony side.

## Follow-up (issue #116)

`attrs.zarrmony.input` recorded the path the user handed to `convert`, and only that path. For a multi-file vendor format the path is an index: a whole-slide VSI stats at 4.4 MB and names 37.2 GB of `.ets` tiles in a sibling directory that hold every converted voxel. So `size_bytes` was wrong by four orders of magnitude, `--checksum` covered an index and would not notice a corrupted tile, and nothing in the record said either thing. Anything ingest derives from those fields — compression ratio, throughput, a "did we get the whole file" check — inherited the error silently. `audit_schema_version` 14.

- **The reader is asked; nothing is inferred.** Bio-Formats already knows, via `IFormatReader.getUsedFiles()`, surfaced by `bffile` as `BioFile.used_files()` and reachable through bioio's `BioImage.reader._bf`. Sibling-name heuristics (`<name>.vsi` + `_<name>_/`) were rejected: they work for exactly one format, and the failure mode of a wrong guess — an audit that confidently names files the reader never opened — is worse than the gap.
- **Three-valued, not two-valued.** `input.files` and `input.size_is_partial` are both absent when no reader could answer. Emitting `size_is_partial: false` there would assert completeness we cannot check, which is the same class of error the issue reports. Ingest branches on presence: absent means unknown, `false` means the named path is the whole input, `true` means it is an index.
- **`size_bytes` and `sha256` keep their meaning.** They still describe the named path. Redefining them to cover the set would have been the smaller diff and a breaking one — a consumer pinned to 13 would silently start reading a different quantity under the same key. The new information arrives under new keys, so 14 is purely additive.
- **`size_is_partial` compares bytes, not file counts.** A directory input whose members the reader enumerates is still fully described by `size_bytes`, since `size_on_disk` already recurses. Only a set that outweighs the named path is partial.
- **`--checksum` gains `input.files.sha256`, a manifest digest.** SHA256 over sorted `<relpath>\0<file sha256>\n` lines, paths relative to the set's common ancestor. Relative paths keep the digest stable when a dataset is moved between filers, which happens routinely in this pipeline; including the names means adding or renaming a sidecar registers as a change rather than only editing one. Omitted for a single-file set, where it would restate `input.sha256`. Digests are memoised on `(path, size, mtime_ns)` because per-scene conversions build one audit record per store and a four-scene VSI would otherwise hash 37 GB four times.
- **The path listing is capped at 64 with `listing_truncated`.** `count` and `size_bytes` are always exact. A VSI names six files; a TIFF series can name thousands, and store attrs are not an inventory system.
- **`inspect` reports the set too, and never hashes it.** Pre-flight is exactly where a user computes the ratio that motivated this issue, and `inspect` promises to be cheap. The CLI's `Input:` and `Size:` lines lead with the bytes actually read and keep the named path's size in parentheses, so the two can never be confused for one another.
