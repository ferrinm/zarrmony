# LIF shading correction: extract references, do not apply

LIF acquisition files carry shading _references_ (id + human name) inside `<InScanProcessing>/<CameraLane*>/<ShadingProcessingStep>` but not the corresponding pixel data — LAS X keeps the shading library on the acquisition PC and does not ship it in exported `.lif` (or `.lifext`) files. Zarrmony extracts the references into the audit's `mosaic.shading_correction` block and emits `MosaicShadingWarning` when references exist but no correction is applied; no correction pass runs in this ADR's scope. Applying the correction is deferred to a follow-up that accepts a user-supplied `lif_shading_library=` path (see issue at bottom).

## Considered Options

- **Apply the correction using pixels from the `.lif` / `.lifext`.** Rejected on empirical evidence: a sandbox spike (2026-07-02, `s3_zarrmony_notebook.org` under the ODC51_astrocytes heading) raw-scanned both files with UTF-16-LE needles. The shading-ref id (`606`) and the human name (`CA21M726010K8 (b/w), 2048x2048, O10x11506537, MagChanger , FLUO`) appear in the 10.87 GB `.lif` exactly 48× and 96× respectively — clean multiples of the 48-scene count, all inside `<ShadingProcessingStep>` reference tags, zero as defining elements. The 2.15 GB `.lifext` sidecar holds LAS X UI cache (elements named `2_pmd_0`, `2_histo`, ...): precomputed projections and histograms, no shading references. `bioio-lif` / `readlif` also refuse to open the `.lifext` (image-count ≠ offset-count in the LMSDataContainerEnhanced descriptor). There are no pixels to correct with in Leica's acquisition-format files.
- **Bundle a placeholder correction (median-of-tiles or per-tile normalization as a stand-in flat field).** Rejected: reversing an unknown shading curve with a synthetic estimator introduces silent intensity distortions indistinguishable from real signal. A user reading `mosaic.shading_correction.applied: true` would consume incorrect quantitative values without any way to tell — a worse failure mode than the current uncorrected pixels. If Leica's actual reference is not available, the correct move is to name the gap loudly and let downstream decide.
- **Silent no-op — extract but emit no warning.** Rejected: mirrors the original bioio-lif auto-stitch failure shape (bad output, no signal). The whole point of a warning class is that a mosaic scene with a declared shading intent AND no applied correction is a load-bearing fact for anyone doing quantitative analysis at tile seams — silence would mean users treating uncorrected output as corrected.
- **Ship the library-lookup path in the same release (introduce `lif_shading_library=` in v0.8).** Rejected: no pilot user has a resolvable library on hand today (Julia's astrocytes LIF references an on-PC-only LAS X library that has not been retrieved; #41 follow-up). Adding a kwarg with no test fixture forces API design speculatively — library format is unverified (assumed plain `.lif`, possibly not), correction math is unverified (multiplicative flat only? per-lane scaling?). Ship the extractor + audit + warning now; land library-lookup as a follow-up once a real library fixture exists.
- **Restrict the warning + audit block to mosaic scenes.** Accepted: single-tile confocal scenes have the same underlying shading falloff but no tile-seam artifact — the visible failure mode driving #47 is mosaic-only. Restricting the surface to mosaic scenes matches how users encounter the problem and avoids emitting 48 warnings on non-mosaic files where the correction gap is not visible. Non-mosaic scenes would still benefit from correction if pixels were available; that's the follow-up's scope.
- **Lift `extract_shading_references()` into `bioio-lif` upstream in this release.** Deferred: the extractor is dependency-free and would benefit all bioio-lif consumers, but the surrounding audit + warning story is zarrmony-specific. Land in zarrmony first; propose upstream after real-world use validates the shape (same pattern as the tile-layout extractor).
- **Auto-detect the LAS X shading library by walking sibling directories.** Rejected for now: even if a heuristic path search succeeded on one microscope's storage layout, silently pulling in a file the user did not name violates the "smart default + user override" pattern (locked v0.1 decision). Explicit `lif_shading_library=` path (in the follow-up) is the only mechanism.

## Consequences

- **New extractor: `zarrmony.metadata.lif_shading.extract_shading_references(scene_xml) -> list[dict] | None`.** Returns one dict per `<CameraLane*>` with `{lane, ref_id, ref_name}`, or `None` when the scene has no `<InScanProcessing>` block. Fail-closed on malformed / oversized / entity-carrying XML — mirrors `lif_tiles.extract_tile_layout` (safe parse, 32 MiB cap, `_EntityRejectingTarget`, `_DOCTYPE_OR_ENTITY` regex pre-scan).
- **New warning class: `MosaicShadingWarning` in `errors.py`.** Fires once per mosaic scene under any auto-stitch cascade path (stage-stitch, grid-stitch, bioio-lif) when `extract_shading_references()` returns a non-empty list AND no correction was applied (always the case in this ADR). Body names each unresolved reference (`ref_id`, `ref_name`) plus the camera-model / objective clause parsed out of the ref_name, so users know what library to hunt for. Not emitted on the `per-tile` writer path (per-tile pixels are written verbatim; correction is orthogonal to the on-disk shape and would apply to per-tile output identically once the library path lands).
- **New audit block: `mosaic.shading_correction: {applied: bool, reason: str, references: list[{lane, ref_id, ref_name}]}`.** `applied` is always `false` in this ADR's scope; `reason` names why (`"reference pixels not present in .lif or .lifext — LAS X shading library required"`). The field exists now so the follow-up's library-lookup work is purely additive: `applied: true, method: str, source_library: str, references_resolved: [...], references_unresolved: [...]`. Recorded on all cascade paths, not only when the extract succeeds — a `references: []` records that the extractor ran and found nothing (distinguishable from the field being absent on non-mosaic scenes).
- **`audit_schema_version` bumps to `9`.** Additive — the new `mosaic.shading_correction` key is optional and older consumers ignore it. The bump signals the schema addition to downstream (Lucida, anything else reading `attrs.zarrmony`).
- **No new `convert()` kwarg in this ADR.** Nothing for a switch to gate against — the extract+warn path always runs when references exist. The follow-up introduces `lif_shading_library: str | Path | None = None`; the current no-correction behaviour becomes the documented default when the path is not supplied.
- **Warning cadence.** `MosaicShadingWarning` fires once per mosaic scene, so a 48-mosaic-scene file surfaces 48 warnings by default. Users who want a single-fire summary use `warnings.filterwarnings("once", category=MosaicShadingWarning)` — same escape hatch as `MosaicStitchingWarning`, no new API. The warning body's identical prefix across scenes ("shading references present but not applied: id=606 …") lets `once` collapse them cleanly.
- **Interaction with existing mosaic warnings.** A mosaic scene can now emit `MosaicStitchingWarning` (bioio-lif fallback), `MosaicPlacementWarning` (stage-stitch overlap mismatch), and `MosaicShadingWarning` simultaneously — they name orthogonal gaps (geometric vs. photometric) and users need both signals to judge output quality.
- **`MosaicMergedSiblingWarning` path is unchanged.** A mosaic scene with a `_Merged` sibling gets skipped in favor of the vendor-stitched sibling regardless of shading — the merged sibling's pixels already have Leica's correction baked in.
- **SemVer: next minor bump (targets the current `[Unreleased]` block; v0.9.0 has already shipped).** Additive metadata, new warning class, audit schema bump. Today's behavior on a mosaic-with-shading-metadata file changes only by the new warning firing and the new audit key appearing — no pixel change, no on-disk shape change. CHANGELOG migration note documents the new warning and the audit key.
- **The `.lifext` sidecar is now documented as "LAS X UI cache" in the LIF reader plugin docstring.** The spike showed it holds precomputed projections (`*_pmd_0`) and histograms (`*_histo`), not shading references. Documenting this saves the next investigator a 30-minute detour.

## Follow-up (issue #48)

Introduce `lif_shading_library: str | Path | None = None`, resolve `<ShadingProcessingStep>` reference ids against the library's images, apply Leica's flat-field correction to raw tiles before stitching. Blocked on (1) retrieving a real library fixture from the acquisition PC and (2) empirically confirming Leica's correction math against a LAS X-corrected reference on the same acquisition.
