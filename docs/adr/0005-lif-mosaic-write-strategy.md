# LIF mosaic write strategy

For LIF mosaic scenes with no vendor `_Merged` sibling, `convert()` keeps today's bioio-lif auto-stitched output as the default and adds a `lif_mosaic` knob (`"auto-stitch" | "per-tile"`, default `"auto-stitch"`) — `"per-tile"` writes one OME-Zarr image per tile under a scene-named group, with the OME `<Plane>` `PositionX/Y/Z` of each tile carrying the LIF stage coordinates so external stitchers (ASHLAR, m2stitch, BigStitcher) can re-stitch correctly. The `MosaicStitchingWarning` body grows a `lif_mosaic="per-tile"` hint so users hitting a bad stitch see the escape hatch in the same message. Implementation tracked in #36.

## Considered Options

- **Keep (a) only — auto-stitch + warn loudly, no opt-in.** Status quo behavior plus #34's surfaced positions and intended overlap %. Rejected: the audit metadata is enough for a downstream tool that already knows to look for it, but the on-disk pixels are still the wrong pixels. A user writing 48 stores to S3 (the `2026-05-14_ODC51_astrocytes` case) has no second chance from the audit alone — they still have to re-run conversion from the source LIF to get tile data. Surfacing the metadata without offering a corrected output path leaves the original problem in place.
- **Flip the default to (b) per-tile.** Pixel correctness is the load-bearing requirement; bioio-lif's 1-pixel-overlap stitch is unfit for quantitative work at tile seams. Rejected for v0.5: it breaks the v0.1-locked "one scene = one OME-Zarr store" invariant (see `project_zarrmony_v01` decision #3) for every existing LIF mosaic user, including ones whose downstream tooling reads the auto-stitched pixels happily (visual QA, low-stakes previews). The smart-default + user-override pattern (the v0.1 design's recurring posture) wants today's behavior to remain the default and the corrected path to be one explicit kwarg away. The default may flip in a future major when the per-tile shape has settled in user pipelines.
- **(c) Refuse without explicit opt-in.** Forces every user of a mosaic LIF to consciously pick a strategy. Rejected: a hard error breaks every existing pipeline (CI, scripted batch conversions, Aperture ingest in the cloud) on the next zarrmony upgrade with no graceful path. The warning + audit metadata already give a sophisticated user the signal they need; the new `lif_mosaic="per-tile"` flag gives them the corrected output. A `--strict-mosaic` mode that escalates the warning to an error can land later if real users ask for it.
- **Per-tile output as a bf2raw-style multi-series wrapper (one `bioformats2raw.layout` bundle per scene).** Considered for the per-tile on-disk shape. Rejected: a per-scene bf2raw bundle would nest a transitional layout (`bioformats2raw.layout` is classified "transitional" in v0.1) inside the canonical per-scene layout, and the OME-XML `<Plane>` carrying tile positions already gives external stitchers the registration data — they do not need a vendor-bundle wrapper to find sibling tiles. A flat directory of per-tile OME-Zarr images under a scene-named group (`<scene>/tile_X{f}Y{f}.ome.zarr`) is the smaller surface and matches the existing per-scene aesthetics.
- **Encode per-tile sub-stores as group children inside the scene's single OME-Zarr store.** Considered as a way to preserve the "one scene = one store" invariant verbatim — each tile would be a multiscales group keyed by `X{f}Y{f}` under the scene's root. Rejected: OME-NGFF 0.5 does not specify nested-multiscales semantics, and tools that recurse into a store expecting one `multiscales` at the root would mis-render. Sibling per-tile stores under a plain directory group are unambiguously two images, which is the truth.
- **Per-scene heuristic: auto-pick per-tile when extracted `intended_overlap_x_pct > N%`.** Considered because the audit now knows the intended overlap. Rejected: a silent on-disk shape flip based on an XML attribute is the same failure mode as today's silent bad-stitch — the user can't predict what they'll get. The flag stays explicit; the warning text quotes the overlap so the user has the number to drive their decision.
- **Hardcode the `lif_mosaic` choice in the LIF plugin's `_MosaicAwareLifReader` rather than as a `convert()` kwarg.** Considered for symmetry with `skip_reason`. Rejected: write strategy is a writer concern, not a reader concern. The reader exposes the tile data and metadata; `convert()` owns the on-disk shape. Threading the kwarg through `convert()` keeps the reader plugin free of format-specific writer policy and matches how `layout=` is already plumbed.

## Consequences

- **`convert()` gains a `lif_mosaic: Literal["auto-stitch", "per-tile"] = "auto-stitch"` kwarg.** The CLI gains a matching `--lif-mosaic {auto-stitch,per-tile}` option (default `auto-stitch`). The flag is documented as "LIF-specific" — other readers ignore it. This is the only new public surface area in v0.5.
- **Per-tile output shape: one OME-Zarr image per tile, nested under a scene-named directory group.** The store path for a mosaic scene `S` resolves to `<output>/<sanitized_S>/tile_X{f:02d}Y{f:02d}.ome.zarr/` (zero-padded grid coordinates from the extracted `field_x`/`field_y`). Each tile sub-store is a self-describing OME-Zarr v0.5 image with its own `OME/METADATA.ome.xml` carrying `<Plane>` `PositionX/Y/Z` (meters → micrometers per OME convention, sourced from `pos_x_m`/`pos_y_m`/`pos_z_m`). The scene-named directory itself is a plain directory (no `zarr.json`), not a zarr group — it's a sibling-collector, not an image. The audit's `mosaic` block grows a `per_tile: true` discriminator and a `tile_stores: [...]` list when per-tile mode is used.
- **`audit_schema_version` bumps to `5`** to mark the new `mosaic.per_tile` / `mosaic.tile_stores` keys. Downstream audit consumers (Lucida, anything reading `attrs.zarrmony`) switch on `mosaic.per_tile` to decide whether to look at sibling stores. Auto-stitch records keep today's shape (`mosaic.per_tile` is `false` or absent, no `tile_stores`).
- **`MosaicStitchingWarning` text gains a closing escape-hatch sentence.** New form: _"… consider external stitching (ASHLAR, m2stitch, BigStitcher) if boundary correctness matters, or re-run with `lif_mosaic=\"per-tile\"` to write each tile as its own OME-Zarr."_ The warning still fires only in auto-stitch mode (the per-tile path doesn't auto-stitch and so doesn't carry the 1-pixel-overlap caveat).
- **SemVer: v0.5 minor.** Today's behavior is unchanged when the new kwarg is omitted, and the audit-schema bump is additive — no existing audit field changes meaning. The CHANGELOG migration note for v0.5 documents the new flag, the per-tile on-disk shape, and the `audit_schema_version` bump. A future v1.0 (or earlier major if real-world feedback warrants it) may flip the default to `"per-tile"`; that flip carries a separate ADR.
- **`MosaicMergedSiblingWarning` path is unchanged.** A mosaic scene with a `_Merged` sibling still gets skipped in favor of the vendor-stitched sibling, regardless of `lif_mosaic`. The flag only governs the no-sibling fallback.
- **Plate-mode interaction (ADR-0004).** A mosaic FOV inside an HCS plate well is a plausible Phenix/Operetta acquisition mode. For v0.5 the plate writer rejects `lif_mosaic="per-tile"` with a `LayoutMismatchError` ("per-tile output is incompatible with plate layout — a plate FOV is one image by spec; convert as flat to get per-tile stores"). Auto-stitch in plate mode behaves as today (each FOV is one auto-stitched OME-Zarr image under the well). Per-tile plate FOVs can land in a follow-up ADR once a real plate-with-mosaic-FOVs fixture exists to drive the shape decision (likely under a sub-group keyed off the FOV path, but premature without data).
- **The bioio-lif fallback path remains under maintenance.** `_MosaicAwareLifReader.xarray_dask_data` still returns `mosaic_xarray_dask_data` for the auto-stitch path. The per-tile path consumes the raw tiled `xarray_dask_data` (with the `M` dim intact) and iterates tiles in `convert()` — no new writer is introduced; `writers.scene.write_scene` is called once per tile with the M-axis sliced out, reusing the single pixel-writing path the codebase already maintains (the same reuse rationale as ADR-0004's per-FOV scene reuse).
- **Stage positions are the source of truth for tile registration.** The OME-XML `<Plane>` `PositionX/Y/Z` per tile is the public surface; tile grid indices (`field_x`/`field_y`) land in the audit `mosaic.tile_stores[i]` alongside the store path but are not the registration mechanism. Downstream re-stitchers read positions, not indices.
