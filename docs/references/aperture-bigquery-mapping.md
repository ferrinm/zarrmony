# Aperture BigQuery ↔ zarrmony field mapping

Reference table for the `calico_aperture.zarrmony_metadata` BigQuery table (schema defined in [`iac-aperture/deploy/arch/bigquery.tf`](https://github.com/calico/iac-aperture/blob/main/deploy/arch/bigquery.tf)). Every column is tagged with one of three owners:

- **user-supplied** — the Aperture ingest form is the source of record; zarrmony does not attempt extraction.
- **zarrmony-supplied** — extracted from the source file into `attrs.zarrmony` by a reader plugin; ingest reads the named audit path.
- **derived** — the ingest layer computes it from a zarrmony field, the GCS transfer manifest, or a submission-time constant.

The audit-shape decisions (`per_scene[i].acquisition`, `per_scene[i].channels`, `output.ome_ngff_version`) are locked in [ADR-0008](../adr/0008-aperture-bigquery-mapping.md). Extractors that populate them ship in issues #61 (channel identity), #62 (LIF acquisition), #63 (CZI acquisition + channels), #64 (ND2), #65 (default / OME-TIFF), #66 (plate identity).

For plate-layout audits, replace `per_scene[i]` with `fields[i]` in every audit path below — the two record types carry the same channel/acquisition surface; only the discriminator (`audit.layout`) and the plate-shape sibling (`audit.plate`) differ. See [ADR-0004](../adr/0004-plate-output-design.md).

The BigQuery schema also defines a `zarrmony_study_submission` table (submission-time form snapshot) and a `zarrmony_study_status_tracker` table (server-managed progress). **Zarrmony populates neither** — both are entirely user-supplied or server-generated. They are summarised in [§ related tables](#related-tables-zarrmony-does-not-populate) for context.

## channel_targets provenance

`channel_targets` in BigQuery names the biological entities imaged (RNAscope target genes, antibody targets, structural stains). The Aperture ingest form is the source of record — the operator knows what they stained for; the source file typically does not.

Zarrmony's audit surfaces per-channel identity in `per_scene[i].channels[i].name`, which may or may not carry target information depending on how the operator labelled their channels during acquisition:

- **Leica RNAscope acquisitions.** LAS X lets the operator name each channel freely; some Calico users have adopted a convention of writing the target gene into the channel name (`"Vegfa"`, `"Pecam1"`). In these files `per_scene[i].channels[i].name` is a legitimate channel-target hint.
- **Generic fluorescence.** Channel names are dye labels (`"DAPI"`, `"AF647"`, `"Cy3"`) or acquisition-order placeholders (`"Ch1"`, `"Ch2"`). The name field carries no target information.

Ingest MAY consult `per_scene[i].channels[i].name` as a fallback when the user's `channel_targets` form field is blank, but SHOULD NOT trust it unconditionally — the same channel name field carries dye labels in the generic case, and the ingest layer has no way to distinguish. When in doubt, mark `channel_targets` as unknown rather than propagate a dye label into a target-name column.

## microscope vs microscope_name

BigQuery separates two microscope-identity fields:

- `microscope` — brand and model, e.g. `"Leica SP8"`, `"Zeiss LSM 980"`, `"Nikon Ti2"`. Recorded by the acquisition software; zarrmony extracts it (see the matrix above).
- `microscope_name` — Calico-internal instance name, e.g. `"Snouty"`, `"Blaze"`. Not recorded in the source file — the operator assigned the name when the microscope was inventoried. **User-supplied via the ingest form**; zarrmony does not attempt extraction and will not populate this column.

The two fields are complementary: `microscope` disambiguates "which brand+model", `microscope_name` disambiguates "which of Calico's three Leica SP8 units."

## Related tables (zarrmony does not populate)

The BigQuery schema defines two adjacent tables that zarrmony does not touch — recording them here so the mapping is complete:

- **`zarrmony_study_submission`** — submission-time form snapshot (PK `id`), one row per study submission. Fields: `submission_id, submission_name_internal, submission_name, canopi_project_code, submission_email, file_extension, source_file_format, created_on, last_modified, imaging_method (REPEATED), microscope, source_file_path, microscope_name, destination_user_file_path, transfer_job_status, user_metadata`. Note that `imaging_method`, `microscope`, and `microscope_name` also appear in `zarrmony_metadata`: the submission table carries what the user declared at form-fill time; the metadata table carries what zarrmony extracted per file. The ingest layer decides how to merge — typically the metadata-table row inherits from the submission unless zarrmony's extraction supplies a value.
- **`zarrmony_study_status_tracker`** — server-managed progress record (PK `submission_id`). Fields: `submission_name, submission_name_internal, num_files, num_files_in_gcs, ome_zarr_status, num_expected_in_tenaya, num_in_tenaya, status, created_at, last_modified`. All values are computed by the ingest / conversion / Tenaya pipelines — zarrmony contributes to `ome_zarr_status` only indirectly via the conversion endpoint's status callback.

The source of truth is [`iac-aperture/deploy/arch/bigquery.tf`](https://github.com/calico/iac-aperture/blob/main/deploy/arch/bigquery.tf). When that schema gains or drops a column, update the ownership table and (if the column is `zarrmony-supplied`) the extractability matrix. Audit-shape changes stay under ADR governance — extend [ADR-0008](../adr/0008-aperture-bigquery-mapping.md) or land a new ADR rather than editing this reference doc silently.
